## 1. Executive Summary

**推奨は D: Adopt Hybrid Acquisition。ただし全方式を同時に作るHybridではなく、「目前の整備相談・履歴確認のために、手元資料から一件の経緯を整理し、後日の結果を同じ件へ返す」C＋限定D＋Gである。** 主な供給源を自発投稿の増加に置く仮説は、次の実験では外す。相談への回答量も供給の代理指標にしない。

入口の約束は「Knowledgeを残す」ではなく、**次の工場相談で、いつ何が起き、何が行われ、何がまだ不明かを説明できる**こと。Document Importを初期供給、Problem-drivenな相談準備を利用理由、Outcome Follow-upを継続の検証対象にする。文書を持たない人には本人の短い観察も受け付ける。一般的な故障診断・修理助言を獲得の呼び水にはしない。

最も疑うべき前提は「書く摩擦さえ下がれば、用途がまだない日に利用者が記録し、後から他人に役立つ粒度へ育ててくれる」である。UI改善は必要条件を整えるが、この動機の前払いを解消しない。ただし、Founderの低利用報告はUGCの失敗を確定する比較実験ではない。

また、**Outcomeのある自動車情報はすでに存在する**。iATNは相談・更新・修理結果を検索する仕組みを案内し、Identifixも技術者由来の確認済み修理情報を販売している[S1](https://www.iatn.net/fix-database)[S2](https://www.identifix.com/direct-hit/mobile/)。機会は「誰も結果を持っていない」ことではなく、到達できる対象群で、仕様・実作業・結果・観察期間・再発がつながった利用可能な記録を、既存手段より安く集めて再利用できるかにある。

**統合Knowledge事業は、条件付きの検証対象として残す。確定した事業中核としては扱わない。** 本人便益、共有可能な独立供給、他者での追加価値、取得運営原価の四つが必要。本人の履歴整理だけ成立すればA事業への縮小、回答だけ好評ならBの独立採算審査、どちらにも選択行動がなければ追加投資停止を選ぶ。

最初に行うのは、Founderの実資料5枚以内で手順を合わせ、外部Owner最大4人・各1案件で行う35日以内、Founder計12時間上限の手動試験。最初の2人が資料提供・確認へ進まなければ、その段階で止める。自社OCR、Web検索、chat、継続schemaは作らない。

## 3. Current Explicit UGC Model

現実の入口はA（明示的UGC）とB（軽量Logging）の混合である。「Knowledgeを書け」と直接要求しているわけではない。本人向け履歴、Journalの楽しさ、同車への関心がすでにある。この強い形の現状案と比較する。

**UGCを維持すべき理由**は、すでに記録を好む少数Ownerなら、自由文が発生条件や失敗を豊かに残し、Founderの回答業務なしで供給できること。急な問題を扱う責任も、資料取込の権利確認も相対的に小さい。接点のある専門的Contributorが継続し、読者が再利用するなら、小さな編集型Knowledgeサービスの方がHybridより強い。多数の一般Ownerを活性化する必要はない。

弱点は、入力時の私的便益が将来にあり、日常写真の供給と結果付き整備実例の供給が違うこと。保存を簡単にしても、来訪する理由、結果を返す理由、他者向け利用許諾は別途必要になる。軽い記録をFounderが後から全て聞き取り直すなら、入力負担が移転しただけである。

因果仮説は `実際の用事 → MECHORIを思い出す → 書く便益が費用を超える → 保存 → 後日確認 → 共有可能 → 他者用途に一致`。現在の改善は主に保存前後を支える。上流の選択と下流の再利用が弱ければ供給事業にはならない。

UGCを反証なしに捨てないため、試験参加者のうち普段から記録する人には既存Quick Record・手元メモの選択を残す。無依頼の記録、Owner総作業時間、後日の使える結果を比較する。実験のために同じ内容を二重投稿させない。

## 4. Problem-driven Acquisition Hypothesis

**「問題を解く」を分解する。採用候補は調査・説明の準備であり、修理の正解を答えることではない。** 相談を自社内で完結させなくても、工場へ渡す経緯と、その後の事実が残れば取得目的は達成し得る。

| Ownerの用事 | すぐ返せる候補価値 | 取得できる事実／取得できないもの |
|---|---|---|
| 異音・警告について工場へ相談 | 本人の観察時点、条件、前回作業、不明点を整理 | 観察と相談履歴。原因確定・運転可否は取得も保証もできない |
| 部品が合うか調べたい | 資料にある番号と仕様差、確認先を取り出す | 購入・装着・使用後の観察を別々に回収。番号一致だけで適合しない |
| 見積もりを理解したい | 作業項目・過去との違い・工場へ聞く点を整理 | 見積もりは予定。実施・価格の妥当性・成功の証明ではない |
| 車検前・次の入庫前 | 手元履歴から前回の記載と未確認事項を探す | 過去事実。安全な状態や必要作業を自動判定しない |

単独便益が先に返れば、記録を後回しにする人にも入口はできる。しかし質問文はまだEvidenceではなく、回答は外部参照かAI整理でしかない。**新しい一次情報は、Owner／実作業者が後から報告するまで増えない。** 回答後に問題が片づくほど、戻る誘因が消える可能性もある。

失敗形は、無料の車相談窓口になり、毎回長い調査が必要で、部品・費用・診断の断定を期待され、結果は工場とOwnerの間にだけ残る状態。相談件数が伸びてもKnowledge取得戦略としては失敗と判定する。

このため初期の仮説は「困ったらいつでもAIに質問」より狭い。**実際の入庫・履歴参照の前後を一件だけ引き受け、本人が使う短い経緯を返す**。自分でGoogleや工場を使った人から結果だけ受け取る経路も同等に比較する。

## 5. Document-import Acquisition Hypothesis

資料取込は、すでに払われた記録コストを再利用する供給戦略である。特に過去履歴の空白を埋め、入力直後に「探せる」価値を返せる。ただし、書類の多さは結果付き独立事例の多さではない。

| 入力資料 | 比較的取り出しやすいもの | 誤って補完しがちなもの |
|---|---|---|
| 整備明細・記録簿 | 記載日、作業記載、メーター表示、記載部品 | 実施者の個人identity、原因、長期改善 |
| 領収書・部品購入履歴 | 購入品、金額、購入時点 | 装着済み、車への適合、改善したこと |
| 写真・Notes | 撮影／記述された状態、本人の言葉 | 実発生日、同案件関係、作業完了 |
| 過去SNS・メール・工場とのやり取り | 明示された観察・説明・報告 | 転載許諾、発言者の確認、結果の独立性 |
| 車検・検査資料 | その時点の検査記載 | 以後の状態、故障なし、全整備履歴 |

手順は `必要な資料だけ選ぶ → 候補へ → 元の記載と照合 → Ownerが分かる範囲を確認 → 私的履歴へ → 必要時だけ共有用抜粋`。一括「合ってる」は未読追認を招く。読取が合っていること、作業が実際に行われたという申告、機械的に正しいことを別に扱う。

Founder Anchor Vehicleの数年分の資料は、欠落・重複・日付精度・再利用方法を試す高価値な材料になり得る。**実資料の存在・利用権は今回未確認**。最初から全数年をデータ化せず、今の一つの問いに必要な5枚以内を選ぶ。答えを取り出せなければ、何百枚取り込んでも価値検証にならない。一台の多数書類を多数の独立修理成功へ数えない。

純粋なDocument-firstへの全面pivotを今は選ばない。初回整理だけで満足する、クラウドフォルダ＋汎用AIで足りる、次の書類が入らない、他者共有を断る、という失敗があるため。**Importした量より、その資料が実際に使われたかを先に判定する。**

## 6. Outcome-driven Evidence

### Outcome gapの判定

**判定: 不足の可能性はあるが、automotive Web全体でOutcomeが主要な不足だとは今回の資料から証明できない。** iATNのFIX Databaseは強い反例[S1](https://www.iatn.net/fix-database)。Identifixの「confirmed fixes」は供給・商品化の存在を示すが、確認品質・継続追跡・MECHORI対象車への網羅性は宣伝文から検証できない[S2](https://www.identifix.com/direct-hit/mobile/)。

iFixitは質問者が解決後に戻らない問題を2009年に記述し、現行Helpでも解決回答の選択と結果コメントを求める[S3](https://about.ifixit.com/c/Answers)[S4](https://www.ifixit.com/News/14191/feedback-loops)。これは結果回収の摩擦が知られている証拠であり、2026年の自動車forumでの欠落率を示す調査ではない。

機会候補は、①結果自体の欠落、②結果はあるが仕様・作業と結びつかない、③長期再発が不明、④公開されず見つからない、⑤存在しても本人の案件に適用できない、の五つ。取得で解くべき①③と、検索・権利・適用判断で解く②④⑤を混同しない。既存情報が十分なら、供給網の新設より本人の資料索引でよい。

### 最小限の結果の意味

`同じ案件を本人が指定 / 誰の観察か / 観察日 / 作業との関係 / 改善・不変・悪化・再発・未確認 / 分かる観察条件`を残す。「直った」一語は入口として受け取り、成功率の確定値にはしない。例えば走っていなければ再発未観察であり、再発なしとは異なる。追跡距離を知らなければ不明のままにする。

無回答、まだ作業前、観察機会なし、確認したが未解決は別状態。改善と再発を両方残し、後の報告で前の報告を消さない。複数部品の同時交換、条件変化、自然消失があれば、作業後の改善を特定部品の因果効果へ昇格させない。定期整備には症状や「解決」が不要である。

Ownerへ返す理由は「前回の経緯を次に使える状態へ戻す」「工場との確認事項を更新できる」。社会貢献や催促だけで返してもらう想定は弱い。Gは有望な補完層だが、初回獲得を単独で担わない。

## 7. Professional-generated Evidence

工場は実施作業・計測・部品の発生点に近い。Ownerの記憶だけより根拠を得やすい一方、納車後の変化はOwner側にあり、工場だけで長期Outcomeは閉じない。実作業者が書いたという出自も、診断の正しさや故障原因の証明とは別である。

Shopmonkeyの公式操作手順では、点検情報を見積・請求とともに顧客へ送り、PDFや写真・コメントの閲覧先を渡せる[S8](https://support.shopmonkey.io/hc/en-us/articles/38744430526612-Send-Inspections-to-Customers)。この例からの推論は、**顧客説明や請求という既存業務の成果物なら、Knowledge投稿より自然に生成される**こと。MECHORI向けに別フォームを埋める理由までは生まれない。

最初はOwnerがすでに受領できる明細・報告を使う。工場に協力を求めるとしても既知の1軒、1件、既存出力＋限定項目の訂正だけ。新しいshop account、顧客台帳、DMS連携、全工程の撮影を要求しない。担当個人・工場・顧客の権利と確認範囲は区別する。

工場側の即時価値は、同じ説明の繰返しや履歴聞き取りが減ること。参加をProfessional有料契約やポートフォリオ願望の証明にしない。既存明細の受渡しすら増分業務になるなら、この取得経路は後回しにする。全国営業で供給問題を解く案は現体制では棄却する。

## 8. External Web vs Proprietary Evidence

| 層 | 含むもの | Knowledgeへの扱い |
|---|---|---|
| External Reference | 公開ページ、他siteの実例、公式資料、参照日・対象範囲 | 内容が真の実体験でも外部由来のまま。要約・翻訳しても自社実例にしない |
| User source / candidate | 本人が持つ明細、原文、AI抽出、Ownerの記憶 | 私的な候補。資料所有だけで第三者権利や作業内容が全て確定しない |
| MECHORI first-party Evidence | 実車・実際のactor／申告者・source・時点・明示関係と確認範囲を持つ記録 | Observation単独でも部分Evidence。完全caseや共有可能なKnowledgeとは別 |
| Shared Evidence | 個別の共有許諾と権利処理を満たす、必要部分のprojection | 他Owner用途への適用範囲と不足を確認して再利用する |

一つのcase内に四層が並んでもよいが、由来を統合して消さない。外部記事を読んだという行動は利用履歴、実車で起きた結果は新しい観察であり、別の主張として結ぶ。内部だから外部の整備資料より正しい、とはしない。

**External dependency↓は目標にしない。** 部品供給、公式仕様、地域制度は外部資料が必要なままでよい。固定した対象問いで、本人履歴だけ／外部付き／独立他車Evidence追加の実用差と原価を測る。内部件数の増加で価値が下がる可能性もある。

Waze型の「自動的に増える」と、iATN型の「実務参加者が結果を返す」は同じ副産物モデルではない。MECHORIの提案は主として後者であり、最後の人間の行動を省略できない。

## 10. Cold Start Analysis

四つの不足を分ける。**本人の履歴不足**は資料取込、**今の問いへの参照不足**は外部資料、**他者へ使える独立Evidence不足**は許諾された別実車の結果、**選ばれる信用・接点不足**は実際の紹介と便益でしか埋まらない。

一台の深い履歴は最初の不足を解けるが、同型車Networkを立ち上げたことにはならない。逆に内部情報が空でも、必要資料を見つけて説明を整える私的サービスは試せる。外部Webを検索できることだけでは、Googleを使う人の乗換えは説明できない。

対象は「全Owner」「Barchetta所有者全員」ではなく、接点があり、散在する資料と目前の入庫／履歴参照用途があるOwner。BarchettaをAnchorには使うが、他者比較に必要な実車と資料が集まる保証を置かない。最小試験で同条件の2組を作れなければ、ネットワーク部分は未検証として止める。人数を1000へ増やして解決したことにしない。

## 11. Single-player Value

**成立し得るが、限定的で未証明。** 本人履歴＋資料＋必要な外部参照＋整理により、前回作業の説明、同じ相談のやり直し回避、出典への到達は提供できる。診断や部品適合が分からなくても、説明と資料探索の具体的な負担が下がれば有意味である。

一方、資料がなく、工場が全履歴を管理し、Ownerが困っていないなら価値は小さい。AIで長文を作るだけ、無料の有人相談が主価値、フォルダ内検索と時間が変わらない場合は否定する。

| 事業 | 成立を示す行動 | それだけでは示さないもの |
|---|---|---|
| A Personal Vehicle History | 別日に自分で履歴を取り出し実際に使う。整理・確認コストに見合う | 他者共有、CのNetwork、継続課金 |
| B Problem-Solving Assistant | 普段の手段より選ばれ、説明・調査準備に具体差が出る | 修理成功、結果回収、独自Evidence |
| C Shared Evidence Network | 別Ownerの許諾済み実例が追加便益を生み、新しい結果が返る | 安全な一般修理法、全車種coverage、利益 |

Missionの最小実現はAによる本人・次の工場への引継ぎでもあり得る。Cが不要なら、その縮小を失敗隠しの「Knowledge事業」と呼ばず、独立のOwnerサービスとして支払・維持原価を検証する。Bだけなら独自性のない相談窓口を保持する理由は薄い。Cが強くAが弱ければ、Owner app全体を拡大せず、少数Contributor＋限定再利用の別案を選べる。

## 12. Network Effect / Evidence Density

**候補は人数そのものではなく、特定の問いに対する利用可能なEvidence密度。** ただしデータを貯める規模の効果と、参加者の追加が既存利用者の便益・次の供給を増やすネットワーク効果は別である。

密度は単一スコアにせず、問いごとに①独立実車・source数、②世代・engine・part・symptom・workの一致／差／不明、③結果観察窓、④気候・市場・法域の必要な差、⑤共有可能性、⑥実用再利用を併記する。情報が増えても条件不一致や訂正負担が増えれば価値は下がる。

「1000人の薄い投稿」対「30台の濃い履歴」は仮想比較であり、30台が常に勝つわけではない。同じ適用範囲の問いなら、出典・結果・反対結果がある30台は比較材料になりやすい。しかし30台が異仕様・同一工場・同じ愛好家群に偏れば独立性もcoverageも弱い。1000人の短い観察が新しい問題の存在を示す方が有用な問いもある。

検証は同じ問い・同じ外部参照へ、独立他車の許諾済みEvidenceを一件足し、説明・比較・不確実性の理解に何が変わったかを見る。次の受益者が結果を返したとき初めて循環の兆候となる。Like・閲覧・内部比率の上昇は代替にならない。

## 13. Generic AI / ChatGPT Substitution Risk

**最大の戦略リスク。** ChatGPT Projectsは会話・資料・指示をまとめ、project memoryとWeb searchを提供すると公式に説明している[S12](https://help.openai.com/en/articles/10169521-using-projects-in-chatgpt)。「車の文脈を覚える」「資料を読める」「出典リンクがある」だけでは独自性にならない。料金・地域・設定による実際の利用可否は比較時に記録する。

| 差別化候補 | 本当に差になる条件 | 崩れる条件 |
|---|---|---|
| Persistent Vehicle context | Ownerが毎回資料を組み直さず使える | Projectへ同じ資料を置くだけで十分 |
| Longitudinal history / recurrence | 訂正・観察期間・再発を後から迷わず辿れる | 日付付きメモ＋検索で同等 |
| Provenance / work-result linkage | 主張単位の出自と未確認が実務で必要とされる | 見た目が整ったsummaryだけを求められる |
| Owner / mechanic participation | 既存成果物を二重入力なく往復できる | 工場の既存systemから出てこない |
| Vehicle succession | 譲渡時に許諾部分が本当に使われる | 数年に一度の価値が取得原価を支えない |
| Independent shared Evidence | 同じ資料を渡した汎用AIでもない実車結果に便益がある | Webに同じ情報があり、または権利上共有できない |

比較相手を「何のcontextもない無料chat」に弱めない。Ownerが普段使う方法に加え、許された範囲で同じ履歴・資料を渡した汎用AI／フォルダも比較する。MECHORIだけFounderが丁寧に整理するなら、その労働分を表示する。差が消えればAI assistantの開発を止める。

本当の防御性が生まれるとすれば、機能数より、利用者が繰返し更新する独立実車の履歴、共有許諾、訂正、他者再利用の関係である。それもまだ仮説。私的データの囲込みや出力制限をmoatにしない。

## 14. Trust / Provenance / Privacy / Copyright

以下は実験・設計の境界であり、法的な適法性判断を確定するものではない。対象資料・利用先が決まっていない段階で「所有資料なら再配布可」「匿名化すれば自由」と扱わない。

- **主張の区別**: 原記載／Owner観察／Owner推測／工場報告／AI候補／外部参照を分ける。Ownerが抽出を確認しても工場確認済みにしない。source、時点、確認者の役割、訂正履歴、明示関係を保つ。
- **欠落と矛盾**: 不明は許容。sourceが矛盾したら両方残す。同じ明細の写真とメールは独立2件でない。検索で見た答えに沿って過去記憶を書き換える誘導を避ける。
- **Privacy**: Quick Recordは現αで参加者共有固定の経路である。原本明細・相談文・個人情報をここへ置く手動実験にしない。既存の許可済み私的手段またはOwner端末での提示を使い、適切な受渡し手段がなければ保存せず観察に留める。
- **最小化**: 氏名、住所、電話、VIN全文、ナンバー、署名、精密な位置、第三者通信は原則受け取らない。工場名も用途に必須か確認し、公開時は別判断。希少車＋日付＋地域の組合せも識別され得るものとして扱う。
- **権利の分離**: 所持、私的閲覧、AI処理、候補保存、限定提示、一般公開、将来の第三者提供は別用途。資料がOwnerの手元にあることだけで工場・撮影者・通信相手の権利を消さない。
- **外部Web**: 原資料へのリンクと必要な短い整理に限定し、全文収集・常設vector化・paywallやbot制限の回避を行わない。URLの存在は再利用許諾の証明ではない。
- **AI境界**: 本番[KNOWLEDGE_SYNTHESIS](KNOWLEDGE_SYNTHESIS.md)の内部事例契約をこのレビューで拡大しない。手動試験も外部AI送信範囲が未承認なら人の転記・整理で行う。AI利用時は送信範囲と処理条件の承認を別に確認し、原本を無条件に渡さない。
- **削除と再検証**: 実験の受領コピーは確認後7日以内、未確定でも受領から30日以内に削除する案。必要な原本はOwnerが保持する。出典位置と確認記録だけ残った場合は「運営が原本を再閲覧可能」と表示しない。仮名計測台帳は最終評価後14日以内に削除／個人追跡不能な集計へ。本人に返した成果物の保持は本人が選ぶ。
- **安全**: 診断・交換指示・運転継続の保証は提供しない。緊急の車両安全判断は実験対象外とし、既存の専門家・緊急対応へ接続する。現実の修理を実験のために実施・延期させない。

権利確認・マスク・訂正・削除・安全確認は、AI原価より大きくなり得る実際の取得原価である。省略してネットワーク採算を計算しない。

## 15. Founder + AI Feasibility

Founder一人でできるのは、対象を絞った資料整理と相談準備の検証。全車種の質問対応、継続督促、全件専門確認、多数工場の導入支援を同時に持つことはできない。AI coding agentが速く実装できることは、実車の確認・権利取得・問い合わせ対応の能力を増やす保証ではない。

実験は新規契約・依存・APIなし、追加のサービス運用費0円を目指す。これは既存運用費が0円という意味ではない。既存固定費の請求は未確認であり、production化の前に合計を確認する。OwnerのChatGPT／Codex利用料は開発費という現ルールを維持し、顧客処理を無制限に肩代わりして運営費0円と見せない。

継続費は `既存固定費＋hosting/DB/storage/auth/mail/監視/解析＋案件数×(検索/AI/OCR/再試行/転送の実費)`。全体で月5,000円以内でも、有料・従量サービスは別の明示承認が必要。現段階でProvider・料金・無料枠を選定しないため、架空単価の採算表は作らない。

取得原価は、**受け取った文書1枚ではなく、再利用可能になった独立case1件**を分母にする。Founder獲得・整理・照合・督促・権利・訂正の総分数と、Ownerの探索・確認分数も併記する。共有許諾後に他者が使ったcaseが0なら、他者再利用1件あたり原価は算出不能であり「安い」としない。

将来自動化するなら、実測で時間の大半を占め、入力と正解確認が可能な一工程だけ。毎回専門調査が必要なら、OCRを作っても原価は解けない。低頻度ゆえ月額課金が弱い可能性は残し、単発整理や限定用途も後で比較する。Professional収益で赤字Owner供給を賄えるとは仮定しない。

## 18. Smallest Useful Experiment

### 一つの試験: 「次の相談に使う一件」を資料から作り、その後を追う

**目的は画面評価ではなく、C→私的便益→G→再利用→別Owner便益という仮説を段階ごとに切ること。** 開始は別タスク。本書作成時点では募集・連絡・upload・資料処理・AI送信は一切していない。

**規模と上限**: Founder Anchor 1台（成績から除外）＋非Founder最大4人、各1主案件・3〜5枚以内。開始から35日以内、Founder計12時間、既存の許可済み手段のみ、新規サービス費なし。実験参加者の交通・部品・修理費を発生させる課題は出さない。

**募集条件**: 接点があり、今後14日以内に入庫・工場相談・前回履歴確認などの実用機会を本人が挙げる人。相談がすでに工場で進んでいてもよい。書類を持たない人の相談入口も観測するが、Import比較の分母は資料を持つ人と明示。少なくとも2人は直近／進行中のcaseで、後日の観察が起こり得る。本人の便益を提供する条件に一般公開や結果返却を課さない。

| 段階 | 実施と返すもの | 何を切り分けるか |
|---|---|---|
| Day 0、最大1.5時間 | Founderが実在資料5枚以内・一つの実用問いを選ぶ。人がsource付き候補と経緯1枚を作る。不明・欠落を残す | 実験の手順と資料から得られない関係。Founderの満足は市場成績にしない |
| Day 1–7、最初の2人 | 「次の相談で説明し直したくないこと」を本人に一件選んでもらう。既存Notes／写真／工場／検索の普段の方法を短く観察。書類を出す・一言書く・何もしないから選べる | 無料の提案への賛同ではなく、実課題と資料を実際に持ち込むか |
| 初回の同日〜翌日 | 候補化し、元記載を示して確認。私的な経緯1枚（観察／作業／現在の不明／source）を返す。一般診断はしない | 転記と確認の負担、何が不足するか、説明に使えるか |
| 2人の判定後、Day 7まで | 少なくとも1人が実資料の提供と確認を終えたら、残り最大2人へ。同じ手順・上限を使う | 2人とも実行しない入口へ人数を追加しない |
| 各人のDay 2–14 | 本人の実際の相談・履歴参照で使う。Founderが工場へ送信・相談を代行しない。使った箇所と目的だけ任意に確認 | Founderへの礼儀と、本人が現実で使った行動を分ける |
| 各人のDay 14 | 初回に合意した場合のみ、結果確認を最大1回。「改善・変化なし・悪化・再発・まだ不明／未実施」を元case指定で受け取る | 無依頼返却と1回確認後の返却を別集計。観察条件・日付を分かる範囲で付す |

| 最終評価 | 許諾された内容だけを本人へ返し、実験コピーを期限内削除。失敗・未回答・機会なしも残して判定 | 実験を継続督促サービスへ延長しない |

### 比較を小さく保つ

**入力比較**: 文書を持つ人ごとに、同程度の短い二つの実作業項目を選ぶ。一つは本人が普段どおり要点を残し、もう一つは候補を確認する。順番を参加者間で交互にし、各方式5分まで。資料を探す・マスクする時間をImport側にも含める。同じ内容を二重入力させず、違う項目の難しさが残るため因果効果・精度優位を断定しない。時間差だけでなく、分からないまま承認した項目と訂正箇所を数える。

**本人便益／汎用AI比較**: 同じ実用問いについて、普段の手段と経緯1枚で、前回項目・不明点・sourceが見つかるかを見る。汎用AIを既に使う人には、承認済み範囲の同じ資料を与えた通常の方法も比較する。新しいAI送信許可をこの実験名目で作らない。比較不能なら「ChatGPT代替リスク未検証」と明記し、勝ったことにしない。

**他Owner Evidenceの追加比較**: 最大4人の中、または許諾済みAnchorとの間で、実際に対象条件を比較できる2組を探す。受益者2人、別の実車由来の最大2件を使う。Owner自身の用途を先に固定し、①本人資料＋外部参照、②同じ材料＋他Ownerのsource付きcaseで、相談準備に増えた情報を比較する。二つの版は体裁・Founder支援時間を揃え、提示順を2人で逆にする。安全上必要な情報は隠さず両方に含める。最後に全資料を渡し、実際にどの出典を使ったか確認する。標本が小さく学習効果も残るので、比較は記述的な追加価値の兆候に限る。

同条件caseがない場合、架空の適合や実験専用の修理を作らない。空の試行として分母に残す。Day 35まで揃わなければQ6/Q7は未検証、Network開発は不許可。Cだけ合格した場合もNetwork成功とは言わない。

**Outcome gapの小さな監査**: この実験の実用問いから最大4検索を先に固定し、各検索の上位3つの関連する独立原報告、最大12件・計60分だけ確認。広告・同一転載・対象外の除外理由も記録する。車両条件／観察／作業／結果／期間／再発／sourceの有無を同じ基準で読む。専門有料DBは未契約なら未評価として分ける。これは対象問いの入手可能性調査であり、Web全体の欠落率推定ではない。結果を見てqueryを選び直さない。

### 手動台帳と時間予算

新規analyticsやDBは不要。実験台帳の列は `仮名参加ID / case ID / 用途分類 / 機会予定日 / 入力方法 / 提供・確認・利用・結果・再利用の時点 / 支援区分 / source参照ID / 共有同意範囲 / 不明・訂正数 / Owner分数 / Founder分数 / 観測満了・欠測`。実本文・車両identifier・明細画像・通信全文をGit、PR、分析ログへ置かない。

時間配分上限はAnchor1.5h、募集・同意1h、4人の初回処理計4h、比較とWeb監査2h、後日確認・再利用確認1.5h、集計・削除2h＝**12h**。一件の初回作業がOwner対応込みFounder60分で止まらなければ、不明を返して超過理由を記録する。無償の裏方作業を枠外へ逃がさない。

手動候補化で試せるのは、受渡し・確認の負担と成果物の価値である。**OCR精度、AI抽出精度、全自動原価は未検証**。人が行った処理をAI性能として報告しない。AI候補を扱う許可が既にある場合だけ、対象・model・実処理時間・人の訂正を別記する。

合格は次の小試験に進む条件であり、PMFや本番開発の承認ではない。最大4人に達しなければ下記の件数を都合よく縮めず、実数・不足・工数を報告する。最初の2人の入口gateを除き、総合判定は観測窓満了時に行う。

| 問い | 数える行動と分母 | 次に進める兆候 | 失敗・未判定の意味 |

| Q1 Problem-solving value | 具体的用途のある全4人のうち、資料箇所を示して相談・履歴参照に実際に使った人 | 2人以上、うち1人は工場との会話に利用。探す／説明する負担の具体差あり | 「便利そう」だけ、または0人ならvalue失敗。1人なら用途を一度絞り直す |

| Q6 他Owner便益 | 事前指定2試行、受益者2人。空検索も残す | 2人とも別実車の出典と条件差を確認、少なくとも1人が現実の相談・確認へ引用 | 無関係／不要ならdensity失敗。資料不足なら未検証。Founder一人の自己評価は除外 |

採用行動を「MECHORI appを選んだ」と誇張しない。既存連絡手段でFounderへ相談した場合は**MECHORIの手動提案を選択**した証拠まで。Founder不在・遅い応答・別の提供者でも選ぶかは次群で検証する。

**共通条件**: 実用成果物に架空の車両条件・部品・原因・作業・結果を確定していないこと、誤共有や未承認送信がないこと、総12h以内。下書きでの誤読は修正量として記録し、Ownerが確認できなければ不明のまま。重大な根拠外主張や情報漏えいがあれば当該配布を止める。

既存[MEASUREMENT_PLAN](MEASUREMENT_PLAN.md)のActivated OwnerやMeaningful Reuseは互換のため維持する。今回の「実用再利用」は表示・出力だけでは足りず、使用目的・箇所・別日が必要。Completed Evidence Loopも、単なる後日返答や過去資料の整理完了と同一視しない。

Founder、QA、架空例、代理入力、最終面談で要求した操作を主成績から分ける。全候補・全同意者・資料保有者・利用機会あり・満了・未回答・辞退を人数で示す。自発の判定には来訪経路だけでなく、本人のきっかけと連絡時点を使い、不明は不明にする。

## 20. Decision Tree After Experiment

1. **実資料と課題が持ち込まれない**: 入口の説明または対象接点を一度だけ変更する。最大2週間・追加4hでも得られなければ、この獲得経路を停止。車市場全体の否定ではないが開発は解禁しない。
2. **Cの提供・確認は成立、Q1/Q5は不成立**: 整理した満足だけ。archive/OCR製品を作らない。必要な用途が見つからなければE（scope削減）へ。
3. **Q1/Q5は成立、相談のQ2は弱い**: C Document-firstへ絞る。本人履歴を次群で反復検証し、chat／Web回答機能を外す。
4. **Q1/Q2は成立、資料取込Q3は弱い**: 限定D＋本人短文＋Gへ。書類必須を外す。結果Q4が成立しなければKnowledge acquisitionの推奨は撤回する。
5. **本人便益とQ4は成立、Q6/Q7が不成立**: A事業へ縮小を検討。共有網を本人履歴の付録として漫然と開発しない。1回だけ対象の適用範囲を狭め、関連資料を用意して反証を確認する。
6. **Q6/Q7は強いが一般Ownerの継続供給が弱い**: 記録を好む少数OwnerのA、または既知工場のFを供給源とする限定Evidenceサービスへ。全Owner app拡張を止める。
7. **Q1–Q7に兆候があり時間上限内**: 推奨Hを、新しい2〜4人で支援を減らして一度再試験。全機能を開発せず、実際の最大摩擦一つだけを改善候補にする。
8. **どの便益も弱い／原価・権利が解けない**: 統合Knowledge事業への追加投資停止を推奨。既存ユーザーの保全・出力を維持する縮小判断へ。

同条件の他者資料や自然な利用機会がない場合はINCONCLUSIVEであり、成功でも失敗率0%でもない。ただし35日を無制限に延ばさず、未検証のC事業へ投資しない。最大一回の修正試験を使った後は、成立した片側だけ残すか止める。

## 21. 90-day Strategy Impact

[Strategy v2](STRATEGY_REVIEW_V2_2026-09.md)の判断期間は2026-09-10〜12-08。本レビューで開始実績を捏造せず、時計を新たな90日に戻さない。以下は採用した場合の再配分案であり、ROADMAPの自動改定ではない。

| 残り期間 | 優先すること | 進行gate／捨てるもの |
|---|---|---|
| 9/16〜9/23 | 実機QA状態と利用機会を確認し、最初の2人・Anchorの素材と権限を確保 | 課題と資料が出なければ募集・入口の問題を判定。Home追加改修を代替にしない |

ROADMAP Phase 1.5の実帳票・自己再利用を実験として前倒しする。Phase 5のOCR実装をそのまま前倒しする意味ではない。共有価値がないと判明した場合、PRODUCTの統合前提と2026-08-16のB2B主利益仮説を置換理由付きで改定する。今回それらの既存決定を削除しない。

## 22. Final Recommendation

**D: Adopt Hybrid Acquisitionを推奨する。実験の順序は C（既存資料）→限定D（本人の相談準備）→G（結果更新）。UGCは任意の観察・Contributor供給として残す。**

- **WHY**: 自発記録の前払い負担を減らし、実世界の用事に先に便益を返す一方、広いAI相談の原価・責任・代替リスクを避けて検証できる。CとDそれぞれの結果不足をGで検証するが、自動的に閉じるとは主張しない。
- **WHAT CHANGES**: 次の検証の入口・対象・成功条件。記録件数ではなく、実用案件の持込、sourceの確認、結果返却、本人再利用、他者追加価値、取得原価を判定する。
- **WHAT STAYS**: 実車中心の履歴、本人原文、Quick Record、Garage、Maintenance、出自・不明・訂正・権利の区別、診断しない境界、低頻度利用の前提。既存UI・データは保持する。
- **WHAT TO TEST FIRST**: 最初の外部Owner2人が、自分の現実の一件に必要な資料を出し、候補確認後の経緯を実用するか。そこが動かなければOCRもassistantも作らない。

**この提案は「投稿アプリからAIアプリへのpivot」ではない。Knowledge Networkを続ける権利を、安い手動実験で取り直す提案である。** AだけでもMissionの一部には意味があるが、Cの取得コストを正当化しない。Cの追加価値が確認できない場合は、E（Knowledge Network thesisを弱めscope削減）を明確に選ぶ。

## 23. Adversarial Review — このRecommendationが間違っているとしたら

**最も強い反論**: MECHORIはまだ現UGCの対象・用事・実機QA・観測期間を揃えていない。低利用を見て、既存UGCより運営が重く、強いAI競合がいる方式へ移るのは早計である。記録すること自体が便益の2〜3人に集中すれば、手動相談より良いEvidenceが安く継続生成されるかもしれない。この反論を退ける実測は現在ない。

| Failure mode | 隠れた前提 | 推奨を反転させる証拠／対応 |
|---|---|---|
| 1 資料を出すまでが最難関 | Ownerの手元資料は見つけやすく共有可能 | 最初の2人とも提示・確認せず、普段の短文記録なら継続。A/Bへ戻す |
| 2 Founderの代行にだけ価値がある | 手動の便益をsoftwareへ移せる | 次群で人の調査・催促を減らすと利用停止。限定有料代行の独立採算以外は止める |
| 3 汎用AIで十分 | provenanceや結果linkが利用者に選ばれる | 同じ資料を渡す通常AI／フォルダで同等以上、別日にMECHORIを選ばない。独自assistant撤回 |
| 4 Outcomeが返らない | 私的履歴を閉じる便益がある | 実際に観察機会がある満了caseでも結果0、1回確認後にしか返らず工数超過。Gを基盤にする仮説撤回 |
| 5 Shared Evidenceに使えない | 私的便益から共有許諾・適用性へ移れる | 非共有希望が主、適用範囲が散る、他者case追加で差がない。Aへ縮小 |
| 6 既存情報で足りる | 対象問いにOutcome gapがある | 固定queryの原資料に十分な結果・条件があり、内部を足しても用途が変わらない。供給網投資停止 |
| 7 熱心なUGC少数が勝つ | 一般Ownerを動かす必要がある | 2〜3人が無支援でsource付き結果を反復供給し、別Owner再利用も起き、取得工数がHより低い。A中心へ戻す |
| 8 工場の既存出力が最も安い | Owner経由が最適な取得点 | 既知工場の通常出力だけで同意・根拠・Owner結果が自然に回り二重入力なし。E/F中心へ切替 |
| 9 資料は増えるが改善の意味が分からない | 文書が必要な関係を含む | 同時作業・不明仕様・未観察ばかりで比較不能。scopeを一用途へ狭め、Graphの万能性を撤回 |
| 10 低頻度の経済性が合わない | 復帰時の便益が維持費を払う | 実用はあるが支払条件で選ばれず、無料利用・supportを賄えない。事業を縮小／停止 |

ほかの隠れた前提は、接点のある4人に35日内の用事があること、少なくとも2つの他車比較が組めること、非公開の受渡しが既存手段で安全にできること、Ownerの「確認」が単なる礼儀でないこと、事故・紛争を避けた安全な対象でも便益が十分あること。いずれも実験で記録し、揃わなければ未検証として投資を止める。

Mission自体への反論も残る。人と車の経験を残す価値があっても、全事実を永続保存する責務と収益が一社へ集まるとは限らない。既存フォルダ、工場帳票、車種コミュニティへの持ち運べる整理だけで目的を満たすなら、巨大な独自Networkを作らない判断が正しい。
