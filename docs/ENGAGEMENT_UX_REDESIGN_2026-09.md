## 1. Executive Design Verdict

**最大の作業仮説は「自分と関係のある車の変化が、次に開く期待へ変わっていない」こと。Social機能の不足だけでは説明できない。** 現行には人・車両フォロー、いいね、Web内通知がある。一方、Homeはフォロー中の初回公開記録の列であり、自分の車・読みかけ・続報への期待が弱い。さらに、実画面の車名リンクから404を確認した。まず期待が途切れる導線をなくす必要がある。

推奨は **C: Hybrid Home**。冒頭に小さな自分の愛車の入口、その下に車両を主語にした有限の「みんなの記録」を置く。新しい意味のある変化を扱う完成形は設計するが、最初の実験は既存の新規記録だけで成立させる。まだないExperience関係を、本文の似方や日付で作り出さない。

「SNS不足」仮説の判定は**部分支持・原因未確定**。Socialの機能数より、①導線の信頼性、②供給の偏り、③読む意味、④小さく残す安心、⑤後日のつながり、の順で検証する。自発再訪は事業価値の代替ではなく、価値検証に参加できる状態を作る先行指標である。

## 5. Engagement Problem Definition

解く問題は「用事がないから利用しない」そのものではない。**短い訪問で、自分に関係のある変化を一つ理解し、必要なら自分の小さな出来事を一つ残せること**が現在どの程度成立するか、である。

Jobは3つ: 「あの車、その後どうなったか」「自分の車、前はどうだったか」「いまのことを忘れる前に残す」。読むだけの日も有効だが、閲覧だけの増加をMission達成に数えない。安全な維持のための記憶を残すことが中心で、故障を娯楽のために煽らない。

目標は1回30–90秒でも価値が分かり、3–7日後に戻る余地があること。これは所要時間の仮説であり、滞在時間を長くする目標ではない。

## 6. Product Pull Model

完成形のloopは **関心のある車の変化→短い経緯→自分の車との想起→本人の記録→後日の結果→読み返し／他者の参照**。人の評判より車の時間が記憶の手がかりになる。

| 段階 | Friction | 見せるもの／返すもの | 確認する行動 |
|---|---|---|---|
| 開く | 何も変わっていない予想 | 自分の車の入口＋実際に記録されたもの。未見ならその根拠を明示 | 自発open、何を見に来たか |
| 気になる | 同じ人物の投稿列 | 車名、出来事の一文、日付。正常な車両リンク | 他車訪問 |
| 読む | 前提／その後がない | CURRENTは車両履歴、後段は明示された同案件の経緯 | 別の記録を読む |
| 自分も残す | 価値ある投稿であるべきという圧力 | 「一文でも残せます」＋自分の車だけを選択 | 無依頼の軽い記録 |
| 保存 | 反応0で終わる | 自分の履歴に加わった実際の1件 | 後日自己履歴を見る |
| 後日の変化 | 元の件を忘れる | 後段で本人が選んだ件に「続きを残す」 | 本人が明示する結果・再発 |
| 再利用 | 写真・感想だけでは適用できない | 出来事、出自、時点、本人の観察、参照元。整理は後で | Self-history用途と他Owner用途を別確認 |

CURRENTで一周できるのは「車両履歴への新記録と見返し」。完成形の同案件loopは未実装。小さな記録がEvidenceになる可能性はあるが、自動昇格はしない。

## 7. Social Layer Principles

Socialは「誰の人気が高いか」ではなく「どの車の経緯を追いたいか」を支える。閲覧履歴から無断でフォロー・通知購読しない。見る相手と見せる相手は別。Usefulや反応を技術的正しさ・工場確認の証拠に変換しない。

| Primitive | CURRENT／提案段階 | Missionへの寄与／採否 |
|---|---|---|
| Follow Person | CURRENT、補助として維持 | 友人の複数車を追う。人を消さず、vehicle主導の隣に置く |
| Follow Vehicle | CURRENT、MUST TEST NOWで既存導線を利用 | 経緯の継続に最も近い。主たるSocial action。「このクルマをフォロー」 |
| Follow Vehicle Model | remoteの現行機能として扱わない。FUTURE | 同仕様Evidenceが複数あるとき有効。車種一致だけで適合を保証しない |
| Follow Experience / Watch update | PROPOSED、TEST NEXTで概念確認 | 特定案件のその後を追う。永続Experienceと購読権限が条件 |
| Save / Bookmark | 本監査で本番対応を確認していない。TEST NEXT | 後で相談・比較するための手がかり。車両Followと同時に新設しない |
| Useful / Helpful | FUTURE、再利用の実態が出てから | 「履歴の確認に使った」等の具体用途が必要。集計人気数は不要 |
| Reaction / Like | CURRENTにLikeあり、新設・拡張しない | 知人への応答はあり得るが結果にはならない。試験で表示優先度は下げ、既存データは保持 |
| Comment | 汎用欄を作らない | 診断依頼・雑談・モデレーション負荷。現段階で継続原材料への利益が不明 |
| Question | TEST NEXTで聞きたい内容だけ検証 | 経緯の不足を聞き、回答を本人Entryに残せる場合。公開質問基盤はまだ作らない |
| Update notification | 既存通知は新規公開中心。意味のある追記通知はFUTURE | 本人が明示購読した対象だけ。見ただけで通知しない |
| Result notification | FUTURE | Ownerの結果報告が入った場合のみ。「解決した」と機械が断定しない |
| Garage visit | CURRENT | 自分／他人の車の集合に戻る。訪問者一覧や足跡は作らない |
| Owner profile visit | CURRENT | 書いた人と車との関係を確認。フォロワー数を価値の主役にしない |
| Vehicle profile visit | CURRENTの一部入口が404 | 最優先で導線整合を確かめる。特定個体の履歴が関心の受け皿 |
| Similar vehicle discovery | PROPOSED、TEST NEXT | 同型がなくても趣味・出来事の関心はあり得る。類似は仕様一致と分ける |

「見た」は自分の端末の読了目印まで。「気になる／続きが知りたい」は当面Vehicle Followに集約。「役立った」は面接で具体用途を聞く。新しい反応ボタンを4つ並べない。

## 8. Home Architecture — 3 alternatives

### A. Feed-first

上から: 小さいHome見出し→最近の記録→車両入口→過去分の終端。記録CTAは共通下部。自分の文脈はGarageへ任せる。供給が十分なら最もすぐに他車が見えるが、現在の疎な供給では昨日の内容が主役になりやすい。

### B. Vehicle-context-first

上から: 自分の選択車→直近の実記録→この車に残す→過去を見返す→他車の最近の記録。Socialなしでも本人価値を出せるが、整備していない日には同じ静的画面になり得る。Garageとの重複が大きい。

### C. Hybrid

上から: 小さい自分の車の入口／draftがあれば復元→みんなの記録の1件目→車両ごとの実記録→終端と自分の過去1件。自分のidentityを短くし、他車の出来事を最初のviewport内へ入れる。Homeは入口、Garageは全履歴とする。

| 比較軸 | A Feed-first | B Vehicle-context-first | C Hybrid |
|---|---|---|---|
| Spontaneous reopen | 供給時に強い／無新着に弱い | 自己用途がある人には強い | 他車への関心と自己用途を両方試せる |
| Social cold start | 弱い | 強いが変化が乏しい | 中〜強。過去と新着の区別が条件 |
| Owner relevance | Followの精度に依存 | 高い | 高い、冒頭を小さく保つ |
| Contribution motivation | 読むだけになりやすい | 自分の記録へ直結 | 他車からの想起と自分の入口を接続 |
| Evidence potential | 他者関心はあるが返却が遠い | Self-historyに強い | 両方に入口。ただし再利用成立は別検証 |
| Implementation complexity | 低 | 低〜中 | 中。最小版は既存projectionのみで縮小 |
| Small-alpha suitability | 低〜中 | 中〜高 | **高、ただし導線正常化と実供給が必要** |

評価は設計上の予測であり実験結果ではない。推奨はC。Bの全面dashboard化も、Aの無限Feed化も採らない。Hybrid自体は既存IA文書にも案があり、本書の新規性は5秒の順序、現在データでの境界、実験条件を具体化することにある。

## 9. Recommended Home

UI名は引き続き「ホーム」。意味は「自分と気になるクルマの最近を知る場所」。画面に英語のmarketing phraseは置かない。

**最初の5秒**で、①自分の車がここにある、②どの車に何があったか、③自分も一文残せる、の3つが分かる。390px幅では見出しと自車入口を合計約150–190px以内に収め、1件目の車名と本文をスクロール前に見せる。画像全体や2件目まで無理に押し込まない。

```text
┌─────────────────────────────────────┐
│ ホーム                          メニュー │
├─────────────────────────────────────┤
│ [自車の小写真] [選択中の愛車名]        > │
│ 前の記録: [出来事の日付] [短い本文]       │
│ ※draftありならこの行を「書きかけを開く」に │
├─────────────────────────────────────┤
│ みんなの記録           [フォロー中]       │
│ [車名]                      [記録日]    │
│ [何があったか分かる本人の本文]            │
│ [その出来事の写真・任意]                 │
│ [出来事の時期]     [このクルマの記録へ]   │
├─────────────────────────────────────┤
│ [別の車／次の実記録]                    │
│ …有限件数…                            │
│ ここまでの記録を見ました                 │
│ [さらに過去の記録]                      │
│ 自分の記録を見返す [実日付＋実本文1件]    │
├─────────────────────────────────────┤
│            ＋ 記録する（共通CTA一つ）    │
│ ホーム    探す    お知らせ    ガレージ    │
└─────────────────────────────────────┘
```

これはPROPOSED最小版。現行の読めるフォロー記録を材料とし、全参加者公開への範囲変更はしない。「参加者の記録」tabはTEST NEXTで、既存権限・projectionが保証する対象だけに限定する。自分の記録を他者の新着に混ぜて件数を増やさない。

最小版は「最近の記録」、将来のtyped changeができてから「最近の変化」。未見保存がなければ「前回から3件」等は表示しない。復元用draftがない日は、書きかけの空枠を作らない。自車なしは短い登録入口と閲覧可能な内容を両立し、既存αの別車種を排除しない。

## 10. Feed Architecture

**Eventを読み、Vehicleへ戻るFeed**を目指す。Vehicleのプロフィールだけを並べても変化は見えず、記録の単純列だけでは連続性が失われる。

### 最小版（PROPOSED / 既存データ）

権限で絞った既存記録→重複ID除去→`publishedAt ?? createdAt`降順。初期上限8件と明示的な「過去の記録」を提案する。連続する同じ車の2件目以降は、車両ヘッダーを共有する短い行に畳めるが、**同案件と名付けない**。同じ車ばかりでも他車があるように見せない。折り畳みは順番・総数を隠すランキングではなく、開いて全文へ到達できる表示整理。

本文の意味をAIで書き換えず、本人の先頭文または本人タイトルを用いる。発生が古く今回記録されたものは「記録: [公開日]／出来事: [実時期]」と併記。最小版は未読・差分追跡を増設しない。

### 完成形の意味のある変化（FUTURE / 明示イベントが必要）

| 変化 | 再掲の扱い | 必要な根拠／依存 |
|---|---|---|
| 新規記録 | 現行timestampで新規として表示可能 | 初回公開日時。出来事の日時とは別 |
| Update／Owner added context | 「補足が加わりました」、差分から該当Entryへ | 明示Entry／revision。単なる`updatedAt`は不可 |
| Result | 「Ownerが経過を記録」＋本人の言葉 | 結果を明示したEntry・観察時点・出自 |
| Recurrence | 過去の改善報告を消さず「再発の報告」 | 同案件への本人指定、再発の時点 |
| Resolved | 「解決したとの記録」、断定的保証にしない | 本人の報告。工場確認とは別軸 |
| Photo added | 内容を理解する新写真なら補足。独立の新着乱発はしない | media追加のrevision、同じ見せる相手 |
| Maintenance completed | 実施報告として表示 | 作業・actorの事実。故障解決とは区別 |
| Status changed | 何から何へ／誰が／いつを表示 | 明示更新。日数経過だけで変更しない |
| 誤字／format編集 | Feedを上げない | 表示上の修正履歴のみ |

完成形では同Experienceの変化を1cardに集約、最新の意味ある変化順。同一車両の別案件を混ぜない。権限撤回／非公開化はFeed・保存・通知の全projectionで再検査する。閲覧済み判定を設けるなら端末限定・対象単位・消去時の挙動を明示し、未読件数を煽らない。

## 11. Experience Card Design

**一目で「この車に、こういう出来事があった」と読めることが最優先。** Ownerは責任と文脈のため残すが、人物avatarを主語にしない。

優先順位は車名→出来事の本文／最新の実変化→日付→写真→Owner→状態／続き。車両の小写真はidentity、本文下のmediaは出来事。写真が同じなら二重表示しない。年式・仕様は違いの理解に必要な場合だけ1行に出す。

```text
┌─────────────────────────────────────┐
│ [車の小写真] [車名]            [記録日] │
│ [年式が既知なら年式]  [Owner名・小さく]  │
│                                     │
│ [本人が残した出来事の一文]              │
│ [続く本文は3〜4行。省略は明確に]        │
│                                     │
│ [出来事の写真 / 任意 / 16:10以内の枠]   │
│ 出来事: [日／月ごろ／時期不明]           │
│ [本人が設定した状態。なければ空枠なし]   │
│                       このクルマの記録 >│
└─────────────────────────────────────┘
  FUTUREのみ: 「経過の記録」[最新本文]
               「これまでの経緯 3件」→同案件
```

Card本体／本文は記録詳細、車名と車両CTAは車の履歴、Owner名はOwnerのGarageへ。重なった全面linkで小さい別linkを奪わない。mediaの拡大は詳細内に集約し、Feedでは本文と同じ詳細へ進む。タップ先を画面間で変えない。

Likeは現行データを維持して補助へ。新設する主Social actionはゼロ、既存Vehicle Followを車両の到達先に一つ置く。Save・Useful・Watchを一斉追加しない。legacy `issue/open`は「記録時: 気になること」と時点を添える案とし、現在の未解決案件数へ集計しない。

## 12. Lightweight Contribution UX

### 4分類の判断

MUST TEST NOWでは4分類を維持する。後から全データの分類を変えるより、心理的受け皿の理解を先に測れるため。「その他」の補助文を**「洗車、部品が届いた、久しぶりに乗ったことなど」**にする。これは入力例で、実在の記録を創作するものではない。TEST NEXTで「日常・その他」への名称変更を比較する。理由は日常経験を例外扱いに感じさせないこと。既存intent値・記録を自動変更しない。

PROPOSEDの導線: Homeの共通CTA→自分の選択車を確認→intent1tap→一文／写真＋一文→共有先の確認→保存。自車は既存の選択に従う。未選択／複数車で曖昧な場合のみ短いpicker。他人の車から押しても、他人のVehicle IDを入力先へ渡さない。

```text
┌─────────────────────────────────────┐
│ 戻る              記録する             │
│ [自分の愛車名]                    変更 │
├─────────────────────────────────────┤
│ [選択した種類]                    変更 │
│ 一文でも残せます。詳しい整理はあとで。  │
│                                     │
│ [本文欄: 何があったかを自分の言葉で]    │
│ [                                    ]│
│                                     │
│ 写真を追加（任意・現行は1枚）           │
│ [選択時だけpreview／変更／外す]         │
│ MECHORIの参加者に見せる                 │
│ 写真にも同じ範囲が適用されます          │
│ [今日の日付]             日付を変える* │
│ [              記録する             ] │
│ 書きかけはこの端末に保存                │
└─────────────────────────────────────┘
 *日付の前倒し表示はTEST NEXT。現在は保存後詳細。
```

MUST TEST NOWは既存textarea・1枚・draftを使う。写真を選んだ人には「どんな一枚か、一言だけ」の補助を出す設計とする。**写真だけ保存はCURRENTではできず、最小試験には含めない**。TEST NEXTで写真のみ需要を確認し、本文必須validation、タイトルfallback、出自・日付・画像privacyを別途設計する。captionをAIで捏造して必須条件を満たさない。

text-firstではintent選択後にfocus。photo-firstでは写真選択前にキーボードを出さない案を比較する。draftは本人の端末に限る現仕様を明記し、写真の再選択が必要なら「写真はもう一度選んでください」。保存済みと書きかけを同じ見た目にしない。

| Ownerの心理 | UIでの応答 |
|---|---|
| こんな小さいことでもよいか | 日常例＋一文で成立するフォーム。完成度badgeを置かない |
| 古い車を誰が見るのか | 車種人口ではなく自分の履歴に残る返却を先に示す |
| 詳しくない／間違いが恥ずかしい | 「見たこと・感じたことをそのまま」。原因の入力を要求しない |
| 面倒 | 自車選択を保持、タイトル不要、詳細は任意 |
| 写真なら出せる | 写真＋短い一言をまず試す。写真のみは別の仮説 |
| その後を忘れる | 自分の過去への入口。将来は本人が選んだ件だけ経過を促す |
| 他の故障が気になる | 驚き・深刻度順で煽らず、経緯とOwnerの観察を読む |
| 同型車／珍しい別車も見たい | Vehicleを先に示す。同型でないことを隠さず探索可能に |

Post-saveは「[愛車名]に記録を残しました」＋保存した実本文の短いpreview。主操作は「ガレージで見る」、副は「閉じる」、詳細補足は折り畳む。反応を待つ画面、共有を強制する画面、未実装の続報slotは置かない。保存後詳細が失敗した場合も、最初の記録が保存済みかを別に示す。

## 13. Experience Continuity / Updates

CURRENT: 車両の時系列と既存記録の編集がある。編集は内容の訂正・補足で、独立した結果Entryの追加ではない。`linkedRecordId`をJournal同士のリンクに流用しない。

PROPOSED完成形は「ひとつの出来事」と「その後の記録」。異音→工場へ→作業→3か月再発なし、というユーザー提示の例も、本人が同案件と指定した場合だけ一続きにする。工場へ持参した事実から、修理した・改善したと推論しない。再発なしは「[本人の観察時点]まで再発なしという報告」であり恒久解決ではない。

続きを残す（FUTURE / 永続Experience必須）

## 14. Garage Redesign

Garageは**自分の車との時間を見返す場所**。現行の本物の写真・所有期間・全履歴は資産であり残す。Homeの短い自車入口に対して、Garageは一台に集中した時間軸を担当する。静的なプロフィール、メンテ時期を勝手に推定するdashboardにはしない。

```text
┌─────────────────────────────────────┐
│ マイガレージ                  設定    │
│ [選択中の愛車]              車を選ぶ  │
├─────────────────────────────────────┤
│ [実際の愛車写真 16:10 / 高さ上限あり]   │
│ [メーカー] [車名・必要なら年式]         │
│ [本人が登録した所有開始からの期間]       │
│ [          このクルマに記録する       ] │
├─────────────────────────────────────┤
│ 最近残したこと                         │
│ [実日付] [直近の本人記録]               │
│ [書きかけがあれば復元入口]              │
├─────────────────────────────────────┤
│ これまでの記録                         │
│ [年／月]                              │
│ [日] [本文] [種別は補助] [写真は任意]   │
│ [日] [本文]                            │
│ [さらに過去の記録]                     │
│ 車両情報・所有履歴・見せる相手 >        │
└─────────────────────────────────────┘
```

「最新状態」は診断summaryにせず「最後に残したこと」と呼ぶ。未解決枠は現在のissue/openから自動生成しない。後段で本人が選んだ「経過を残したいこと」を最大1件出す。所有の節目は既知の日付からだけ表示、不明な開始日を補完しない。走行距離は本人の最後の観測値＋日付、予測メーターにしない。

「この頃の記録」は実在の過去1件、古い日付を目立たせる。季節の整備指示に変換しない。写真を眺め、前の経験に出会う余地はあるが、毎回ランダムに並べ替えない。選車は冒頭、現在／以前の愛車を区別し、選択変更後の履歴を別車と取り違えない。

## 15. Navigation Redesign

主4項目を**ホーム／探す／お知らせ／ガレージ**へ用語統一する提案。「通知」→「お知らせ」は既存UI用語集に合わせる。最小実験では位置とrouteを維持し、一度にナビの学習まで変えない。「記録する」は共通の明示CTA1つ、Garageと入力画面ではその画面の主操作へ統合し重ねない。

Homeは最近、Garageは自分の全履歴、探すは目的を持った横断探索、お知らせは自分が関係を選んだ相手から届いたもの。`/feed`は既存リンクの互換性を保ちHomeに統合する将来案。現行詳細の固定「フォロー中へ戻る」は入口の履歴へ戻し、直接link時だけ安全なHomeへfallback。

desktopは同じ4つを先に、プロフィール・つながり・ヘルプ等を補助群へ。Professionalと管理は資格のある利用者の補助領域に残し、一般Ownerの記録導線から外す。ロゴ再設計、全route改名、新しいアプリ構造は不要。

## 16. Search’s Role

Searchは「いま見て楽しいもの」を並べる主Feedではなく、過去の経験に目的を持って戻る場所。PROPOSED: 「記録・クルマ・人を探す」の1欄→結果種別ごとの区切り→必要時だけ絞り込み。初期viewportに検索欄と実行ボタンが入る。症状、部品番号、結果、危険タグは詳細条件へ。

Owner／車の発見は現行探索能力の範囲を明示。検索をしなくても既存の読める車へ進める入口を置く案はTEST NEXT。同型でなくても閲覧可能にし、Barchetta固定DEMOを全利用者の検索範囲に見せない。仕様一致・出典・状態の確認はEvidence利用時に必要で、見た目の似た車への興味とは分ける。

0件は「条件に合う記録はありません」、取得失敗は再試行。未検証の知識をAIで埋めない。検索語を本人の体験とみなして記録本文へ自動コピーしない。Open Web Groundingをここへ本番追加しない。Self-history検索と他Owner Evidence reuseの評価を別に残す。

## 17. Owner / Vehicle Identity

Vehicleは関心の主語、Ownerは書いた人・経験した人として表示する。Homeの車名→愛車ページ→その車の過去記録、Owner名→その人のGarageという一貫した階層にする。Authorと実作業者を同一人物と決めつけない。

CURRENTのProfileはつながりと3つの数値が先に出る。PROPOSEDは「[表示名]さんのガレージ」→本人の短い紹介（任意）→現在の車→以前の車→読める記録。所有期間は車の文脈で示し、投稿数・フォロワー数を大きな実績にしない。既存のつながり管理は消さない。

車名の表記揺れは[Vehicle identity方針](VEHICLE_IDENTITY.md)に従い、Ownerが登録したラベルを勝手に仕様確定しない。珍しい車を見たい関心は歓迎し、同型がないOwnerの価値を下げない。将来の所有者移転・Mechanic portfolioはこの画面改善の条件にしない。

## 18. Visual Design System Direction

目標は「愛車の出来事が、静かに積み重なっている感じ」。顔を作るのは**実際の車の写真、車名、日付と短い記録が同じ秩序で現れること**。新しい装飾部品ではない。

白い面に墨色の本文、穏やかな細線、少量のteal。日付の小さな欄と本文の並びをFeed／Garage／保存後で共有し、正式な整備書のように見せすぎない。日本語本文と写真が主役。表紙型hero、輪やbadge、装飾メーター、カードの多重入れ子は追加しない。

Current tokenは背景`#f4f5f3`、brand `#2d6177`、accent `#d6a62f`。PROPOSEDはcanvasを白に寄せ、teal候補`#0F6B67`を操作・現在地だけに使う。ロゴの既存accentを即変更する提案ではない。色の移行はTEST NEXT以降で、最小のPull実験では既存色を維持しても情報構造を検証できる。

視覚的な署名は「Vehicle identity→記録の時点→その人の言葉」の反復。最新という小さな印は本当の変化だけに付ける。新規性は親しみやすい情報の順序から作り、感傷的なcopyや生活ブランドの演出に寄せない。

## 19. Typography / Spacing / Density

以下はPROPOSEDの方向値。pixel-perfect仕様ではなく、長い日本語・写真なし・疎なデータでも成立するための制約である。

| 項目 | 基準 | 意図 |
|---|---|---|
| Layout width | mobileは幅いっぱい＋左右16px、320px時は12–16px。本文列はdesktopでも最大約680px | 大画面で文章と写真が過大に伸びない |
| Wide layout | 約1024px以上でside navigation＋本文1列。Garageは写真とidentityを2列にできるが履歴は1列 | ダッシュボードの多段gridにしない |
| Spacing rhythm | 4 / 8 / 12 / 16 / 24 / 32px。関連する情報8、本文とmedia12、記録間24、section間32 | 日付・車名をばらばらに浮かせない |
| Heading | 画面22–24px、主要車名24–28px、card車名16–18px、本文16px | 35px超の見出しで最初の画面を占めない |
| Metadata | 原則12–13px、淡すぎない。状態・操作は本文と同等の読みやすさ | 重要な車名を11pxの補助文字にしない |
| Japanese rhythm | 本文line-height1.6–1.75、見出し1.35。数字だけ等幅桁を許容 | 日本語の読み取りやすさを維持 |
| Typeface | 現行system stackを基礎に和文fallbackを検証。新規font配信なし | 費用と読み込みを増やさない |
| Card boundary | Feedは1px下罫線、影なし。まとめ枠を使っても一重だけ | 記録が続く秩序を作る |
| Radius | content 0–4px、button6px程度、sheet上端12px程度。人物avatarのみ円形可 | 巨大な丸い箱で面積を浪費しない |
| Border | neutral候補`#D9DEDB`。入力境界・選択状態は十分な視認性を別検証 | 全ての情報を囲まない |
| Elevation | 常設内容0、modal/sheetのみ弱い影。浮動CTAは重ならない配置を優先 | 光・glow・glassを使わない |
| Accent | tealは主操作、現在地、明示された変化の印。本文や写真背景に大量使用しない | 意味のない色付けを避ける |
| CTA | 画面の主操作1つは塗り、副はoutline／文字、管理・削除はmenuへ | 同格の保存・共有・詳細を並べない |
| Status | 短い日本語＋必要ならicon。改善報告／未確認／公開範囲を別に | 緑だけで安全・修理完了を保証しない |
| Timestamp | Feedは記録日、別行に発生時期。Garageは発生時期が主 | 「今日追加」と「今日起きた」の混同を避ける |
| Time precision | 日、月ごろ、年ごろ、時期不明を維持。相対表示だけにしない | 古い記憶を正確な日付に見せない |
| Icon rule | 既存Lucide、18–20px、線幅統一、操作には名前。状態をiconだけで伝えない | 新しい依存と謎の記号を増やさない |

Feedの短文は3–4行で折り畳み、詳細では全文。単語・改行の途中で重要な否定が見えなくなる場合は省略表示を明確にする。本文を勝手に要約して「改善した」に短縮しない。初期viewportに2card全部を入れるために文字を小さくしない。

## 20. Image / Media Treatment

車両identityの小写真は正方形40–48px、Garageの主写真は16:10を基本に高さ約200–240pxから調整する。写真が主役になる閲覧モードは後段に分け、日常のGarage入口では履歴へ届く高さを優先する。

Feedの出来事写真は横長16:10程度、縦写真は高さを抑えて全体を見られる余白表示を許す。cropする場合も車体・記録対象が切れないことを確認し、詳細で原比率へ戻れるようにする。故障箇所の写真を車両のプロフィール写真として転用しない。写真なしでも空の画像枠を出さず、車名と本文だけで同じ情報階層を保つ。

CURRENTのQuick Recordは1枚、詳細Journal等の複数mediaとは能力が違う。最小試験では枚数を増やさない。動画、reorder、private object media正規化、元画像の扱いはMECH-046に依存する。Feed用の見栄えのために外部画像取得やAI製造を追加しない。

ナンバー・顔・自宅・明細などの写り込み確認は保存前の具体的な説明で支える。α参加者共有と一般Web公開は別。既存写真の表示不良は隠してfake placeholderに置換せず、「写真を表示できません／本文は残っています」＋再試行・原因に応じた本人の選び直しを示す。権限なしでは写真の存在や説明を漏らさない。

## 21. Motion / Feedback

Motionは変化の理解に限る。押下／選択120–160ms、保存後の短い確認150–200msを上限目安とし、紙吹雪・カウント上昇・常時脈動を使わない。新着挿入で読んでいるcardを押し下げず、「新しい記録を見る」を本人が押した時だけ反映する完成形にする。

保存中は二重送信を防ぎ、「記録中」。長引く場合は写真・通信の状態を説明し、完了前に成功画面へ移さない。最初の保存と共有／詳細補足の部分失敗を区別し、失敗後は入力保持と再試行を示す。保存後は本人の車に実際に加わった記録を返す。

戻る際は直前のcardとscroll、選車、検索条件を復元する。reduce motion設定では移動animationを省略。screen readerへ保存状態を短く通知し、dialogを閉じたら起点の操作へfocusを戻す。これらの実機検証は未実施。

| 車あり・記録なし | 「このクルマの最初の記録を残す。一文でも大丈夫です」 | 架空timeline、埋めるべき多数の空欄 |

| 新しい記録なし | 「新しい記録はありません」＋日付付き過去記録1件 | 毎回同じものを「新着」にする |
| 古い記録しかない | 「これまでの記録」と実時期、並び順を明示 | 単に掲載し直して新鮮さを偽装 |

## 23. Small Alpha Cold Start Strategy

少人数で保証できるのは「新着がある」ではなく「見られる実体験と自分の履歴へ戻れる」。供給をUIで捏造できないことを実験の前提にする。

| 材料 | 方針 |
|---|---|
| Founder / Anchor Vehicle | 普段に本当にあったことだけ。週30分以内の整理・通常記録を目安にし、毎日演出する義務を作らない |
| 既存testerのActivity | 本人の共有範囲で既存記録を利用。車種を理由に排除しない。初回支援・代理入力は別集計 |
| Update resurfacing | typed updateができてから。現行編集時刻を疑似新着として使わない |
| 過去の興味深い経験 | 古い日付・「過去の記録」を明示。最小版は自分の直近過去1件まで、閲覧ランキングなし |
| 所有の節目 | 本人が登録した開始日のみ。TEST NEXT、祝賀badgeや投稿義務なし |
| Unresolved / maintenance follow-up | 後段で本人が「経過を残したい」と指定した件だけ。時間経過から問題が続いていると推定しない |
| Garage changes / 新しい車 | 登録・写真変更を自動で共有事件にしない。公開意思と変更イベントの設計が先 |
| 同型・類似車 | 読める実車があるときだけ表示。存在しない一致車の空枠を量産しない |

実験開始前に各人が「読んでみたい車」を任意で選ぶ。選択を頼んだ時点の閲覧はpromptedとして別扱い。Founderへの強制Followはしない。テスト投稿の識別は本人の用途確認で行い、誤字・短文だけで機械的に除外しない。

第2週はFounderが意図的に追加の盛り上げ投稿をしない。自然な記録は残してよいが、供給のOwner別内訳と運営時間を残す。非Founder供給がなく、自分の履歴への再訪もないなら、Feed中心の投資を縮小する。自主性を作るための毎日の督促はしない。

## 24. Mobile UX

390pxのiPhone相当と412pxのAndroid相当で構造を検討し、320–430pxで長い車名・本文・文字拡大を人間QAする。実機のkeyboard／browser chromeは今回のviewport画像では検証できない。

- Bottom navigationはsafe areaを含む実占有高さを本文下余白へ反映。末尾のリンクや写真を隠さない。現在地は色＋ラベルで示す。
- 片手の主CTAは下側に一つ。入力時は共通FABを消す。Keyboard表示中は保存操作が見えるか、無理なく到達できる位置に保つ。viewport高さ固定でtextareaを切らない。
- PhotoはWebの既存file pickerを使う。camera／GPS許可を先に求めない。pickerキャンセルで本文を失わない。外部appへ移って戻ったときの保持を確認する。
- iOSの戻るswipe、Androidの戻る、画面内の戻るで同じ文脈へ復帰。未保存の本文・draftがある場合は保持状態を示す。空のフォームを閉じる際に確認dialogを乱発しない。
- 選車は小さいsheetでもよいが、Quick Record本体はrouteを持つ1画面。長文やkeyboardのためにsheetの入れ子を作らない。
- 完了sheetは内容が長ければ内部scroll可能、閉じる操作を常に到達可能にする。主CTAをstickyにする場合はfocusされたfieldを隠さない。
- Feed→詳細→戻るでscroll復元。別タブで開いたdeep linkはHome／車両の安全な入口へ。route不在を新機能のように隠さず先に解消する。

Native camera、background upload、GPS自動記録、push、offline syncはFUTURE。90日Freezeを理由なく解除しない。今回のLoopは通常Webの閲覧と入力で試す。

## 25. Accessibility

本文contrastは通常文字4.5:1以上、大きい文字は3:1以上を検証する。teal候補や薄いmetadataを採用しただけでは適合とはいえない。[W3C: Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

主要操作は押しやすさの設計目標として44×44 CSS px以上を確保する。WCAG 2.2 AAのTarget Size Minimumは24×24 CSS pxを基本とし、間隔等の例外がある。44をAAの必須値と誤記しない。[W3C: Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

固定navや保存barでkeyboard focusを完全に隠さない。設計上は全体が見える状態を目指す。[W3C: Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)

headingは画面h1→sectionh2→記録見出しの順。本文の省略には全文への名前付きlink、画像に内容を捏造しない代替text、装飾画像は空alt。写真・色だけで車両や状態を区別しない。入力labelはplaceholderだけにしない。エラーを該当fieldとsummaryへ関連づけ、保存後のfocusが迷子にならないようにする。

Human QA: VoiceOver／TalkBackでHome→車→記録開始をたどる、keyboardだけで操作する、200%文字拡大、320px reflow、reduced motion、長い日英ラベル、通信失敗・写真なしを確認する。今回の監査は適合認証ではない。

## 29. Minimal Vertical Slice

選ぶのは **「気になるクルマの記録を見る → 自分のクルマに一文残す → 自分の履歴で見返す」** の一つ。完成形のExperience Updateをこのsliceへ無理に含めない。

|---|---|---|
| Home | 自車入口1行、Vehicle主語の有限Feed、記録日／出来事の日の区別 | 既存の権限内記録・時刻・選択車。新着差分schemaなし |

Home→他車→Recordでは自車に切り替わったことが分かる。保存後のGarageは書いた車を選択済みにする。車両履歴から記録詳細へ戻れることがsliceの完走条件。

概算作業枠は既存構造を使うfrontend変更＋限定計測／手動記録の準備＋QAで3–5開発日を上限目安とする。見積もりは実装監査前の仮説。projection不足でDB／API追加が必要ならその枝を縮小し、全面基盤へ拡大しない。2週間は**QAを通ったslice公開後の観測期間**で、実装・公開承認待ちを含めない。

実験用の画面がstatic prototypeだけなら、5秒理解・操作意思まで測定可能。自主的な本番再訪への効果は検証できないと明記する。今回の依頼はdesign onlyなので、slice公開と実験はまだ開始していない。

## 30. Two-Week Alpha Engagement Experiment

### 問いと母数

問いは「少ない実供給でも、読むことが車両への関心と本人の記録へつながり、数日後の無依頼の再訪が起きるか」。既存αを車種や整備知識で選別しない。参加同意者全員N、観測14日満了者、本人申告の利用機会あり／なしを別掲する。Founderは主成績に含めず供給者として記録。3人を標準例とし、実数を開始前に固定する。

### 実験前の成立条件（観測14日の外）

- 404、誤った共有先認識、保存に関する重大な不具合を実機QAする。コード成功とHuman QA成功を分離する。
- 過去3–7日の利用日と来訪理由を一度だけ本人に確認する。回想値はbaseline参考であり、厳密な比較対照ではない。
- 各人に他車の実記録を最低1件見られる機会があるかを確認。なければSocial exposure不足として記録し、Self-history部分は継続して検証する。
- 「使う用事があるときに、いつも通り使ってください。使わなかったことも結果です」と一度だけ説明。毎日の課題、投稿ノルマ、Founderへの返礼を求めない。
- 計測方法・除外基準・連絡窓・工数上限・基準値を結果を見る前に固定。既存の同意と収集範囲を超える計測を勝手に追加しない。

### 14日間

| 期間 | 実施 | 評価への扱い |
|---|---|---|
| Day 1 | 短い導入、5秒の理解確認、権限／保存の確認 | 全てprompted。自発利用には含めない |
| Day 2–7 | 通常利用。日々の催促なし。困った際のsupportは受ける | Day 1連絡から48時間以内は誘発の可能性ありとして主集計から除外 |
| Day 8–13 | 同じUIを維持。Founderは実験目的の追加供給をしない | 非Founderの自発利用、自己履歴への戻り、供給なしの日を観察 |
| Day 14 | 最後に15分程度の面接。使った日・動機・覚えている車／記録を確認 | 面接開始後の操作はprompted。感想と実行事実を分離 |

Nが小さいため有意差のA/B試験と呼ばない。途中でナビ・色・通知を追加せず、複数変数の切り分け不能を増やさない。baseline比較は記述的、次cohortまたは反復で検証する。

### 計測の現実と方法

CURRENT: coreに`session_started`、`feed_viewed`、`journal_saved`等の定義がある。しかしlocalは一部イベントをUTC日単位で重複除去し、端末内保存。remoteは設定が有効な場合の月次activity集約で、session別の詳細時系列ではない。Homeには`/feed`と同じ閲覧発火がない。**既存数値だけから自発session、3–7日return、二台目の閲覧、Feed→Record転換を復元できない。** イベント定義の存在を計測済みとしない。

新規外部analytics・DBを必須にしない最小法は、本人が任意に手元へ残す「利用日／きっかけ／見たものの種類／残したか」の短いメモ＋Day 14の一回確認＋既存の保存事実。メモのためにMECHORIを開く必要はない。未記録・思い出せない利用は未確認とし、ゼロや成功に置換しない。日記自体が利用を促す可能性も限界として残す。

次の実装タスクでより確かな導線を測る場合だけ、同意を得た端末内の限定イベント記録を選べる。導入するなら14日＋集計後7日で削除、外部自動送信なし、本文・写真・車名・検索語・位置を収集しない。匿名参加コード／時点／画面種別／入口／当session内の別車判定だけを候補にし、Ownerを追跡する新しい横断IDを作らない。実装・受領は今回未実施。以下の指標は必要データが揃うものだけ報告する。

| 指標 | 定義と分母 | 最小観測方法／限界 |
|---|---|---|
| Spontaneous reopen | 別日に自ら開いた人／同意N。督促・課題・support・通知link由来を除く | 本人メモ／面接で動機を確認。直接流入だけでは自発と判定しない |
| Unsolicited sessions | 30分以上離れた活動を1sessionとする将来の操作定義。無依頼かつ人の利用 | 現行集約では不可。手動は「利用回」の参考値として表示し同一視しない |
| Feed viewed | 画面名だけでなく実記録1件を読んだと確認できた利用 | 未変更の`feed_viewed`件数で代替しない |
| Another / second Vehicle | 同じ利用中に自車以外の車へ1台／異なる他車へ2台到達した人／Feed閲覧者 | 車名を公開集計しない。本人の記憶は補助、route到達障害も記録 |
| Lightweight Record | 本人の実車に一文等の日常記録を自力保存した人／同意N | `createdAt`等の保存事実＋本人用途。DEMO・テスト・代理入力除外 |
| Feed→Record | Feedを起点として同じ利用内に自車の記録開始／保存した利用 | 限定イベント未実装時は本人申告の参考値。保存率に捏造しない |
| Experience updated | 永続Experienceへ後日Entryが追加された数 | **CURRENT未対応／NOT MEASURABLE**。新しいJournalや誤字編集を算入しない |
| 後日の経過記録（代替） | 本人が元の件を指し、後日観察を別記録／補足で残した人 | 本人確認した候補数。構造化continuationとは別集計、本文で自動照合しない |
| Return within 3–7 days | 初回の自発利用から3–7日内に再度自発利用した人／その7日観測窓が満了した人 | Day 7までに起点がある人を主窓に。後発は未満了を別表示 |
| Self-history use | 自分の記録を別日に確認・相談等へ使い、箇所を示せた人 | Strategy v2の30日価値とは別の短期兆候 |
| また見たい | 誘導なしで車／出来事と理由を具体的に述べた人数 | 「好き」「良くなった」だけは弱い。意思と実行を分ける |

連絡ログは時点・種別のみを実験ノートへ残す。通知経由は別集計し、製品内の能動通知も「自分で思い出した再訪」と混合しない。実験の催促等から48時間以内は保守的に主集計から外す。Founder、Codexの今回の監査、再読込、ログイン作業、開発QAを除く。連絡内容や参加者の個人情報をPRへ貼らない。

### Interview（Day 14）

「最後に開いたのは、何を見ようと思ったときでしたか」「覚えている車や出来事はありますか」「残すほどではないと思ってやめたことはありますか」「同じ件のその後をどこに残したかったですか」「開かなかった日は何が足りなかったですか」。最初からSNS・続報・Homeの改善案を答えとして渡さない。

## 31. Success / Failure Indicators

以下は小さい次試験へ進むための暫定基準で、PMFや因果効果の判定ではない。N=3–5を想定し開始前に固定する。例N=3なら「半数以上」は2人。

| 判定 | 条件 | 次の判断 |
|---|---|---|
| CONTINUE | 同意Nの半数以上が別日の自発再訪を2回以上、かつ半数以上に3–7日return。さらに非Founder2人以上が自力の新記録または別日の自己履歴利用を示す | 小さい次試験へ。どの段階が詰まったかで1つ選ぶ |
| Social pull兆候 | 他車を具体的に覚えて再訪した人が2人以上。その車への到達事実もある | Vehicle文脈を維持。まだEvidence reuseとは呼ばない |
| Contribution兆候 | 非Founder2人以上が無依頼で軽い実記録を保存 | 入力の負担とその後の見返しを追加確認 |
| Continuity需要 | 非Founder2人以上が元の件を指して後日経過を残そうとした | MECH-045の小さい概念試験へ。現行更新成功とは扱わない |
| PIVOT | Feed閲覧は増えるが記録も自己履歴利用もない | 閲覧中心の拡張を止め、B案のSelf-history入口を比較 |
| Founder依存 | 第2週にFounder供給を減らすと全利用が止まり、本人履歴利用もない | Feed供給拡大へ投資しない。本人用途を優先 |
| FAIL / 投資停止 | 導線・保存が正常で実記録へ触れる機会もあるが、非Founderの自発再訪が0–1人で具体用途もない | このHome仮説への追加機能を止め、面接で価値・機会を再評価 |
| INCONCLUSIVE | ログイン／保存障害、観測不足、他車供給なし、計測不能 | 原因と人数を明示。成功ともProduct全体の失敗とも判定しない |

比較には全N、満了人数、欠測、Founder比率、実供給のあった日、supportの有無、機会あり／なしを添える。成功の分母を「よく使った人」へ変えない。再訪が増えても、数か月後の結果・出典・他車適用は2週間では証明できない。

Guardrail: 共有先の誤解・公開後悔、新規の重大な情報漏えい、投稿を期待される心理圧力、入力消失は当該実験を止めて評価する。単に未解決・再発報告が多いことは悪化とみなさない。平均いいね、滞在時間、DAU、投稿総数だけを成功条件にしない。

## 32. Risks of Becoming a Generic SNS

### Red Teamと修正

| 批判 | 本案の弱点 | Finalへ反映する修正 |
|---|---|---|
| Generic SNS化 | Feed＋Followだけなら似る | Vehicleの履歴が到達先。新規反応機能ゼロ、有限Feed |
| Missionが薄まる | 軽い写真・短文だけが増える可能性 | 車・原文・時点・出自を保持。全投稿のKnowledge化を強制しない |
| 見るだけになる | Hybridでも読む方が楽 | 非Founderの記録／自己履歴利用を継続条件に追加 |
| Contribution増加の根拠が弱い | 自車入口が書く動機になるのは未検証 | 件数予測をしない。保存しなかった心理まで聞く |
| 少人数で成立しない | UIは実供給を増やせない | Supplyを別記録。0件を隠さず、自己履歴での価値も判定 |
| Founderが投稿し続ける必要 | Anchor車が実質番組になる | 第2週の追加演出なし、週30分の供給工数上限 |
| Evidenceに繋がらない | 短文が後日整理される保証はない | 保存数をEvidence数にしない。本人の後日用途・結果を別観察 |
| 実装コスト過大 | Updates・未読・購読を足すと基盤事業になる | 最初のsliceから全て外す。3–5日枠を超える依存は縮小 |
| Architectureを壊す | Journalを疑似Experienceに改造しがち | linkedRecordId流用禁止、同案件は契約後。現在の時系列を活用 |
| Visual novelty優先 | 新しいtimelineやtealだけで成功した気になる | 実験は既存色でも可能。構造を先、好み評価を後 |
| 過去の再提示で水増し | 古い投稿を新着と誤認させる | 実日付・過去ラベル必須、最小版は自己過去1件まで |
| 通知が再訪を作っただけ | 現行通知と督促が混ざる | 通知由来は別集計。新しい通知systemは作らない |
| プライバシーの摩擦を下げすぎる | 「簡単に投稿」が共有後悔を生む | 共有先は省略しない。公開範囲変更や拡大は別判断 |

Red Team後の修正は明確である。**最初のsliceにExperience Updateを含めない。見た件の自動購読・新着差分表示・全参加者Feedも必須にしない。** 完成形の価値は設計しながら、現在のデータで誠実に測れる問いへ縮小した。

### 33.8 Garage

| 項目 | 仕様 |
|---|---|
| PURPOSE | 自分の車との時間を見返す |
| FIRST THING USER SEES | 選択車・実写真・直近の記録へつながる入口 |
| PRIMARY ACTION | このクルマに記録する |
| SECONDARY ACTION | 過去記録、選車、車両情報 |
| CONTENT HIERARCHY | 選車→identity一度→直近記録→全履歴→管理 |
| VISUAL HIERARCHY | 写真と車名は残すが高さを抑え、日付と本人本文を主役へ |
| INTERACTION | 車の切替とscrollを保持。実時系列を段階表示し全文到達可 |
| EMPTY STATE | 写真なしは車名、記録なしは短い最初の記録入口 |
| LOW-ACTIVITY STATE | 本当の過去1件、所有期間など既知の文脈。メンテ推測dashboardなし |
| MOBILE BEHAVIOR | 選車は上、管理は下、履歴を二重の表に入れない |
| WHY USER RETURNS | 所有物の管理ではなく、自分が過ごした時間が残っている |

### 33.9 Vehicle detail / 愛車ページ

| 項目 | 仕様 |
|---|---|
| PURPOSE | その一台の閲覧可能な経験を知る。CURRENTの404導線を先に整合する |
| FIRST THING USER SEES | 車名・実写真・誰の車か＋最新の閲覧可能な記録 |
| PRIMARY ACTION | 他者: このクルマをフォロー。本人: このクルマに記録 |
| SECONDARY ACTION | この車の履歴を読む、OwnerのGarageへ |
| CONTENT HIERARCHY | Vehicle identity→最新記録→過去→必要な仕様・出自 |
| VISUAL HIERARCHY | 車の写真と車名を主、仕様は必要時。公開範囲を明示 |
| INTERACTION | Garageと同じ履歴表示原則、権限に応じたaction。フォロー変更は確認済み能力内 |
| EMPTY STATE | 閲覧可能な記録なしを明示。非公開件数は出さない |
| LOW-ACTIVITY STATE | 昔の出来事を古い時期のまま表示。新着を偽装しない |
| MOBILE BEHAVIOR | 短いidentity→記録、戻るで元のFeed cardへ。404の代わりに無関係な自車へ飛ばさない |
| WHY USER RETURNS | 人物の投稿列ではなく、気になった一台を追える |

### 33.10 Search

| 項目 | 仕様 |
|---|---|
| PURPOSE | 過去の記録・車・人を目的に沿って見つける |
| FIRST THING USER SEES | 検索欄と検索ボタン、対象範囲を平易に表示 |
| PRIMARY ACTION | 検索する |
| SECONDARY ACTION | 対象／詳細条件、既存の人・クルマ探索 |
| CONTENT HIERARCHY | Query→結果種別→原記録→仕様／出典。結果のないAI要約なし |
| VISUAL HIERARCHY | 検索欄を主、専門filterを畳む、結果の車名と原文を優先 |
| INTERACTION | submit後に結果へfocus、戻るとquery・条件・scroll保持 |
| EMPTY STATE | 条件に合う記録なしと取得失敗を分ける。未知を埋めない |
| LOW-ACTIVITY STATE | 範囲が限られることを表示。Barchetta DEMOを本人の対象と誤認させない |
| MOBILE BEHAVIOR | 最初の画面に実行操作、詳細条件はsheetまたは開閉領域、keyboard保持 |
| WHY USER RETURNS | 「あの時」を探し直す／使える根拠へ戻る用途がある |

### 33.11 Navigation

### Notificationの補足設計

CURRENTのWeb内お知らせを維持し、新しい通知systemは最小sliceに作らない。PROPOSEDの代替は、Homeの実記録と車両履歴への入口そのもの。単に閲覧したExperienceの更新は自動配信しない。Vehicle Followの新規記録通知と、将来の案件購読による続報通知は別の選択として説明する。

後段で導入するなら、明示購読・意味あるEntry・閲覧権限を条件にまとめて通知。誤字修正・古い記録の再掲・未解決の日数経過では送らない。通知理由と停止操作を同じ画面に置く。自分の件へのfollow-upは本人の希望時期を選べる場合だけで、systemが変化したと仮定しない。push・emailは今回の前提にしない。

### Before → After → Why

| BEFORE（CURRENT） | AFTER（PROPOSED） | WHY |
|---|---|---|
| 人名が先、車名は小さい | 車名と出来事を先、Ownerを添える | その一台の経験を記憶しやすい |
| 一部の車名linkが404 | 権限内の実到達先／明示fallback | 興味を持った瞬間の行き止まりを除く |
| Homeの自車入口はFeed末尾 | 冒頭の短い自車入口 | 読む日にも本人の履歴へ戻れる |
| 初回公開順だが発生日だけが目立つ | 記録日と発生時期を区別 | 古い出来事の新規記録を誤解しない |
| 同じ車のcardが長く連続 | 車両単位で見出しをまとめる有限列 | 密度を上げつつ架空の別車を作らない |
| 「その他」が日常の受け皿 | 日常例を明示、名称変更は次試験 | 小さいことを残す許可が伝わる |
| 公開範囲の参照文だけ | 「MECHORIの参加者に見せる」と具体表示 | 心理的負担を説明不足で隠さない |
| 保存後の未来slotが続報を示唆 | 保存した実記録とGarageへの返却 | まだない機能への期待を作らない |
| 詳細は大見出しと写真が先 | 短い出来事の本文→写真→全文・根拠 | 写真の向こうで何が起きたか分かる |
| 詳細の戻り先はFeed固定 | 入口とscrollへ戻る | 探索・自己履歴の文脈を失わない |
| Garageでidentityが繰り返される | identity一度→最近の記録→全履歴 | 車の魅力と見返す速さを両立 |
| Profileの件数・期間が大面積 | Ownerと現在／以前の車が先 | 人気・投稿能力を示す場にしない |
| 検索の専門条件が冒頭を占める | 1欄＋必要時の詳細条件 | 車を探したい軽い用途を阻害しない |
| 編集と新しい結果の関係が曖昧 | 訂正と明示Entryを分離（後段） | 結果・再発・原文の出自を保存 |
| Likeと通知が関与の主手がかり | Vehicleを追う／自分の履歴へ戻る | 反応なしでも便益を返せる |
| イベント名から利用を推測し得る | 自発／促された利用、欠測を分離 | Product Pullを計測の錯覚にしない |

## 34. Final Recommendation

**Hybrid Homeを、小さいVehicle履歴の入口として試す。** 最優先はEUX-01の404導線、共有先理解、読める実記録への到達。次に車を主語にしたFeedと自車入口をつなぎ、既存Quick Recordの軽さを伝える。色・装飾・新しいSocial機能を先に増やさない。

最重要変更TOP 5は、①車への行き止まり解消、②自車文脈＋他車の記録のHome、③車・出来事・時点のcard階層、④一文の許容と共有先を示す記録入口、⑤保存した記録から自車の履歴へ確実に戻る返却である。

これで確かめるのは「読める→覚える→自分も残す→別日に戻る」。同案件の経過、結果、他Owner Evidence reuseは完成形に必要だが、Journal同士を疑似連結して先取りしない。2週間で無依頼の再訪と自分の利用が見えた場合だけ、その次の一つの摩擦へ投資する。

この提案でさえ、供給がなく本人の履歴にも用途がない状態を解決する保証はない。戻る理由が生まれなければSocial機能を増やして先延ばしせず、Strategy v2のSelf-history value検証へ戻す。
