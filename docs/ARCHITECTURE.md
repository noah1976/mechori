# ARCHITECTURE

## 文書の位置づけ

この文書は、初期実装で守る責務境界と、将来拡張に備えて初期データ設計から考慮する事項を示します。ローカルプロトタイプは実装済みですが、データベースと外部サービスには接続していません。

技術候補は方向性であり、実装決定ではありません。初期実装、将来拡張、公開前対応を分け、所有者確認が必要な選択を先取りしません。

## 想定構成と責務境界

| 境界 | 主な責務 | 境界外とする責務 |
| --- | --- | --- |
| Web（Next.js候補） | 入力、閲覧、検索、ユーザー確認、公開操作、管理導線 | 永続化や外部Provider固有処理への直接依存 |
| 将来のExpoアプリ | モバイル向け入力・閲覧、端末機能の利用、共通ユースケースの呼び出し | Web固有UIや特定バックエンドSDKへの業務ロジックの密結合 |
| 共通ドメイン／ユースケース | 車両、整備記録、公開ナレッジ、確認状態、安全制約、権限判定 | UI、OCR、AI、Storage等の実装詳細 |
| Supabase候補 | 認証、永続化、権限制御、Storage等の基盤機能 | OCR・AI判断、公開可否の業務判断、UI |
| OCR Provider | 紙・PDF・写真からの文字抽出 | 抽出内容の正しさの確定、公開判断 |
| AI Provider | 抽出内容の構造化、候補生成、翻訳補助 | 整備事実の確定、安全保証、ユーザー同意の代行 |
| 外部サービス | メール、Storage、監視等の個別機能 | MECHORYの権限・安全・公開ルールの決定 |

Supabase、Next.js、Expo、Vercel、OpenAI API等は現時点の候補です。業務ルールは特定製品から分離し、採用は設計確認と所有者承認の後に行います。

## 設計原則

- 業務ロジックをNext.js、Expo、Supabase等の固有実装へ密結合しない。
- データ型、入力検証、多言語コード、権限判定、公開・確認ルールをWebと将来アプリで共有しやすくする。
- プライバシー、安全性、権限制御、出典管理、確認状態および監査可能性を、初期データ設計から考慮する。
- 管理画面、法的対応画面、完全なモデレーション機能等の実装が後段でも、データ構造を全面変更せず追加できる境界と安定した識別子を初期段階で設ける。
- 税率、法的期限、料金、利用上限、外部サービス仕様をコードへ固定しない。
- OCR・AIの結果は候補であり、人間による確認前に確定記録や公開ナレッジとして扱わない。

## 初期データ設計で考慮する情報

- 内部ユーザーID、車両ID、整備記録ID、共有ナレッジID等の安定した識別子
- 所有者、閲覧者、編集者、運営者等の権限判定に必要な関連
- 手入力、紙、PDF、写真、既存ナレッジ等の出典種別と参照情報
- 原本そのものを保持しない場合にも追跡できる、取得日時、処理方法、原本の削除状態等の最小限の出典メタデータ
- 項目ごとの確度、AI生成・補助の有無、AI処理状態、使用したProvider種別および処理時点
- 未確認、確認済み、要訂正等のユーザー確認状態と確認者・確認日時
- 作成、修正、確認、公開、非公開、匿名化、削除等の訂正履歴・監査イベントを関連付けられる識別子
- 非公開、公開申請中、運営確認中、公開、公開停止等の公開状態

監査可能性は、必要な変更事実を追跡できることを指します。個人情報や原文を無制限にログへ複製することは避け、目的、保存期間、閲覧権限を公開前に定めます。

## 取込から保存までのデータフロー

1. ユーザーが紙を撮影するか、PDF・写真を選択する。
2. 取込前に対象範囲と外部送信の有無を示し、必要な同意を得る。
3. OCR Providerが文字を抽出し、処理状態と出典メタデータを記録する。
4. 必要な場合のみ、AI Providerが抽出内容を整備記録の候補へ構造化する。AI出力には確度と処理状態を関連付ける。
5. UIは原本または抽出元と候補を比較できる形で提示し、ユーザーが修正・確認する。
6. ユーザーの明示的な確認後、確認済み整備記録として個人領域へ保存する。
7. 原本は標準で恒久保存せず、一時処理後に削除する。保存が必要な例外では、目的、期間、同意、削除方法を明示する。
8. 共有を選んだ場合のみ、個人記録とは別の公開候補を生成し、匿名化、安全確認、運営確認を経て共有ナレッジとして公開する。

途中失敗や再処理に備え、取込、OCR済み、構造化済み、ユーザー確認済み、保存済み、原本削除済み等の状態を区別します。未確認の候補を自動で確定・公開しません。

## 個人記録と共有ナレッジの分離

- 個人の整備記録を正本とし、初期の公開デフォルトは非公開にする。
- 共有ナレッジは、ユーザーが明示的に公開を選んだ内容から作る別データとして扱う。
- 共有時は氏名、連絡先、住所、正確な位置、登録番号、車台番号、原本画像等の識別情報を除去または一般化する。
- 個人記録の訂正・削除と、共有ナレッジの訂正・非公開化を別の状態遷移として扱い、必要な関連だけを内部識別子で追跡する。
- 匿名化後も再識別リスクを評価し、安全・法的理由による公開停止や訂正を可能にする。

## データ出力、削除、匿名化

- ユーザー単位で、本人に属する車両・整備記録・添付メタデータ・確認履歴を特定し、機械可読な形式で出力できる境界を設ける。
- 削除要求では、本人データ、処理中データ、Storage上の一時原本、派生データを追跡できるようにする。
- 法令、安全対応、不正防止等で即時削除できない情報は、対象、根拠、期限、アクセス制限を区別して扱えるようにする。
- 共有ナレッジは個人記録と分離し、削除、非公開化、識別子の切り離し、匿名化のいずれを適用するかを公開前に定める。
- 匿名化は表示名の削除だけでなく、自由記述、画像、車両固有情報、時刻・場所の組合せによる再識別可能性も対象にする。

## Provider境界

OCR、AI構造化、翻訳、Storage、メールは、共通インターフェースとProvider別Adapterの境界を設ける方針です。Provider固有のID、状態、エラーは境界内で正規化し、ドメインデータへ直接浸透させません。

各Provider境界では、少なくとも入力・出力の型、処理状態、タイムアウト、再試行、重複実行防止、費用・利用量、送信データ範囲、保存期間、削除方法、監査用参照IDを扱えるようにします。ローカルモックまたは手動運用で設計を検証した後、必要になったProviderだけを導入します。

## 環境分離

- 開発、検証、本番で、データストア、Storage、秘密情報、外部サービス資格情報、送信先を分離する。
- 本番の個人データを開発環境へ複製しない。検証には合成データまたは適切に匿名化したデータを使う。
- 環境を識別できる設定を持ち、誤送信、誤公開、誤削除を防ぐ。
- 本番アクセスは最小権限とし、操作記録、バックアップ、復元、緊急停止を公開前に検証する。

## 初期実装

- 車両、整備記録、作業、部品、症状、結果、出典、確度、AI処理状態、ユーザー確認状態、公開状態、訂正履歴を中心概念としてデータモデル案を作る。
- 認証情報とアプリケーションデータを分離し、アプリケーション側では内部ユーザーIDを使う。
- 個人記録と共有ナレッジを分離し、公開はユーザーの明示操作と運営確認を経る。
- Provider境界を先に定義し、外部接続前はローカルモックまたは手動処理で検証できるようにする。
- ローカルプロトタイプではnpm workspacesと`apps/web`、`packages/core`、`packages/shared`、`packages/i18n`を採用する。本番構成の最終確定とはせず、境界の検証に利用する。

## 将来拡張

- Expoアプリから共通ドメイン・ユースケースを再利用する。
- OCR、AI構造化、翻訳、Storage、メールのProviderを要件や地域に応じて追加・差し替える。
- 管理画面、法的対応、完全なモデレーション、詳細な監査照会、データ出力・削除のセルフサービス画面を追加する。
- 有料プランの処理量・管理機能・専門機能の権限差と、将来の広告枠を追加できるようにする。

これらの後段実装のために、初期段階から識別子、状態、権限境界、出典、履歴の関連を保持します。ただし、不要な個人情報や原本を将来用途だけを理由に収集しません。

## 公開前対応

- 認証方式、権限モデル、Supabase採用時のRLS設計とテスト
- 個人記録から共有ナレッジを作る匿名化・運営確認フローの確定
- 利用規約、プライバシー通知、同意、データ出力・削除・訂正手順の確認
- 危険領域タグ、安全警告、通報、緊急非公開化、監査アクセスの運用確認
- 原本の一時保存期間、削除保証、例外保存、バックアップ対象の確定
- 開発・検証・本番環境、環境変数、秘密情報、バックアップ、復元の分離テスト
- Providerごとの送信データ、保存期間、費用上限、停止・切替・障害時手順の確認
- AI・OCR結果の表示、確度、ユーザー確認、訂正履歴が追跡できることの確認
