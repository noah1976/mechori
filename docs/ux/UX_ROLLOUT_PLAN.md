# MECHORI UX Rollout Plan

## 前提

- `CURRENT`: P-074のナビゲーション試験実装は反映済み。人間の実機UX確認と残りの画面整理は未完了。
- `PROPOSED`: 既存の認証、保存、公開範囲、RLS、写真保護を壊さず、画面単位・導線単位で改善する。
- `NEEDS_DECISION`: Release開始前に、下記の未決事項から該当範囲を確定する。

各Releaseは一つのCodexタスクで全て実装しない。小さな作業単位ごとに、コード確認、対象テスト、型確認、build、人間QAを分けて進める。

## Release 1: 言葉と導線の整理

| 項目 | 内容 |
| --- | --- |
| 目的 | 初見ユーザーが「どこで何をするか」を説明なしで把握できるようにする |
| 対象画面 | ホーム、Garage、記録開始、記録詳細、公開Garage、設定、下部ナビゲーション |
| 変更内容 | 用語統一、主ボタン整理、ホームとGarageの役割分離、下部ナビゲーションを4項目へ整理、右下FAB「記録する」、ハンバーガーメニュー、内部用語の置換 |
| 実装しないこと | 保存方式変更、DB変更、通知、AI、Professional、外部共有 |
| DB変更 | なし |
| リスク | 既存ユーザーが慣れたラベルを見失う。リンク先の誤変更。モバイルでナビが窮屈になる |
| 人間QA | 5秒で現在地と主操作が分かるか。投稿者・車両・記録へのリンクが誤遷移しないか |
| ユーザーテスト | 3〜5人に「愛車を開く」「記録を残す」「友人を探す」を説明なしで試してもらう |
| 完了条件 | `UI_TERMINOLOGY.md`の主要語が対象画面で統一され、各画面の主操作が一つに絞られる |
| 推奨Codexモデル | GPT-5.6 Terra、高推論 |
| 推奨実装単位 | 1. 文言とARIAの置換、2. 下部ナビ、3. ホーム／Garageの導線、4. 人間QA |

## Release 2: 記録開始から完了までの統一

| 項目 | 内容 |
| --- | --- |
| 目的 | 「さっと記録」「詳しい記録」を意識させず、写真や一言から安心して記録を残せるようにする |
| 対象画面 | 記録開始、記録入力、車両選択、写真、公開範囲、下書き復元、記録完了、愛車タイムライン |
| 変更内容 | 記録開始フロー統一、段階的入力、空状態・読み込み・エラー・完了状態の統一、下書き復元との統合 |
| 実装しないこと | 新しい下書きDB、画像バイナリの端末保存、AI生成、公開範囲の緩和、写真の別公開設定 |
| DB変更 | 原則なし |
| リスク | 既存の保存経路・写真処理・編集保存・P-069回帰。下書きが誤って削除される |
| 人間QA | 写真あり／なし、日付が曖昧、車種不明、通信失敗、下書き復元、公開範囲変更、編集保存 |
| ユーザーテスト | 実整備をしていない週に、思い出・今日の一枚・部品交換をそれぞれ記録してもらう |
| 完了条件 | 初見ユーザーが「どれを選べばよいか」で止まらず、保存後にGarageで増えた履歴を見られる |
| 推奨Codexモデル | GPT-5.6 Terra、高推論 |
| 推奨実装単位 | 1. 入口統一、2. 入力情報階層、3. 下書き・失敗状態、4. 完了導線、5. 回帰QA |

## Release 3: 探す・再訪する

| 項目 | 内容 |
| --- | --- |
| 目的 | 故障時以外にも、人・クルマ・記録の変化を理由に戻れる体験を作る |
| 対象画面 | 探す、ホーム、公開Garage、記録詳細、通知センターP-073、下部ナビゲーション |
| 変更内容 | 探すの改善、P-073通知センター、再訪導線、将来の未読バッジに備えた情報構造 |
| 実装しないこと | Push通知、アプリアイコン未読数、ランキング、コメント、DM、AI推薦、全体公開の拡大 |
| DB変更 | P-073の通知データ設計時のみ別判断。Release 3の前提として確定しない |
| リスク | 通知がノイズになる、フォロー関係の重複、非公開・ブロック境界の漏えい、MAU目的の過剰通知 |
| 人間QA | 通知の対象・既読・未読・権限外遷移、ホーム新着との重複、ユーザー／車両フォローの差 |
| ユーザーテスト | 1週間後に自発的に開く理由、同車種または友人を探す理由、通知を邪魔と感じないかを聞く |
| 完了条件 | 通知なしでもホーム・Garageが使え、通知がある時だけ対象の記録へ安全に戻れる |
| 推奨Codexモデル | GPT-5.6 Terra、高推論 |
| 推奨実装単位 | 1. 探すの文言と結果、2. 通知データ設計レビュー、3. 通知一覧最小版、4. 再訪QA |

## 未決事項

| # | NEEDS_DECISION | 選択肢 | 推奨案 | 推奨理由 | 決めない場合の影響 |
| --- | --- | --- | --- | --- | --- |
| 1 | 下部ナビの項目数 | 4、5、6項目 | 4項目（試験実装済み） | 閲覧領域を絞り、記録はFABへ分離できる | 人間QAで通知・ガレージ・探すの発見性を確認できない |
| 2 | 「記録する」の強調 | FAB、中央タブ、Garage内のみ | FAB（試験実装済み） | 主操作を常時表示しつつ、ナビの閲覧領域を圧迫しない | safe areaや入力画面との重なりを人間QAで確認できない |
| 3 | ホームの中心 | フォロー投稿、愛車要約、均等 | 愛車要約を先頭、フォロー投稿を次 | Owner Firstと再訪の両方に合う | フィードのコピーかGarageのコピーになりやすい |
| 4 | 「みんなの記録」の範囲 | フォロー中のみ、α参加者全体、分離 | フォロー中を基本に明記 | 公開範囲の誤解を減らす | 一般公開と誤解されやすい |
| 5 | 愛車ページとタイムライン | 別画面、同一画面、タブ | 同一ページ内 | 一台の時間軸という価値が伝わる | 車両情報と履歴を行き来して迷う |
| 6 | 記録開始の最初の選択 | お題、カテゴリ、自由入力、モード | お題＋自由入力 | 専門知識なしでも始められる | クイック／詳しいの違いを理解させる負担が残る |
| 7 | 公開範囲を置く位置 | 先頭、写真の近く、保存直前 | 保存直前 | 文脈がそろった時に一度だけ確認できる | 早すぎると内容がないまま判断、遅すぎると見落とす |
| 8 | 通知の置き場 | 独立タブ、ホーム内、設定内 | 独立タブ＋ホーム要約 | 通知の履歴とホームの現在地を分けられる | 再訪導線が散在する |
| 9 | プロフィール編集の置き場 | 下部タブ、Garage内、設定内 | Garageのメニューから設定 | 日常画面を管理画面化しない | プロフィールと車両の関係が切れる |
| 10 | 「公開」の説明 | 公開のみ、参加者に見せる、詳細選択 | 「見せる相手」＋具体的な範囲 | α内共有と一般Web公開を混同しない | 写真・本文の共有範囲を誤解する |
| 11 | 記録詳細の主反応 | いいねのみ、コメント、保存 | αではいいねのみ | 安全・運用負担を増やさず反応需要を検証できる | コメントを先に足すとモデレーションが必要になる |
| 12 | Service Briefの見せ方 | Garage内、記録詳細、別ルート | 別ルートを維持 | 専門家向け・将来機能を一般の記録体験と混ぜない | 一般利用者に内部・業務用概念が露出する |

## 実装順序の判断

1. P-074設計レビューで、未決事項1〜7を最小限決める。
2. Release 1を文言・主操作・ナビゲーションの小タスクへ分割する。
3. P-071／P-072の人間QAを通し、Release 2で保存・下書き・完了を壊さない前提を確定する。
4. P-070の初回表示速度を計測してから、Release 1／2で初回表示を重くする変更を避ける。
5. P-073のデータ設計は、Release 3開始前に別タスクで判断する。
