# MECHORI Information Architecture

## 前提

- `CURRENT`: 現行にはホーム、フィード、Garage、人・クルマ検索、プロフィール、記録作成、設定、フィードバック、管理画面がある。
- `PROPOSED`: 利用者の基本概念を「愛車」「愛車の記録」「人・クルマ」とし、画面の役割を整理する。
- `CURRENT`: P-074試験実装では、4項目の下部ナビ、ハンバーガーメニュー、右下の記録作成FABを採用した。PCの常設左サイドバーとハンバーガーの二重化は修正対象である。

## PROPOSED: 下部ナビゲーション

スマートフォンでは、次の4項目を表示する。

1. ホーム
2. 探す
3. 通知
4. ガレージ

「記録する」は下部ナビへ含めず、右下FABから既存の記録作成導線へ進む。設定、言語、招待、フィードバック、ログアウト等はハンバーガーメニューへ格納する。管理画面は管理者だけがメニューから開き、一般ユーザーの下部ナビゲーションへは置かない。P-075AのつながりとP-073の通知は実画面へ接続し、その他の未実装画面は404にせず準備中として扱う。

## PROPOSED: PCナビゲーション

PCでは常設の左サイドバーへ主要導線と補助導線を統合します。ハンバーガー、drawer、overlay、右下の「＋記録する」FABは表示しません。「記録する」は左サイドバーに一箇所だけ置きます。

左サイドバーの順序は、Home、Search、Notifications、Garage、Connections、Profile edit、Invite、Language、Feedback、Help、Settings、Terms、Privacy、Admin（管理者のみ）、Logoutを基本とします。PC上部の重複したMECHORI表示や同じリンクの二重表示は整理対象です。SPでは従来どおり上部ハンバーガー、下部ナビのHome / Search / Notifications / Garage、右下FABを使います。

## CURRENTからの移行原則

- `CURRENT`: フィード、Garage、People、プロフィール、作成ルートが独立している。
- `PROPOSED`: ホームは「今の愛車＋フォロー中の変化」、探すは「未知の人・クルマ」、Garageは「自分の履歴」に役割を分ける。
- `PROPOSED`: 記録作成の入口を複数残しても、到着先の言葉と操作順は統一する。
- `IMPLEMENTED_NOT_DEPLOYED`: P-073の通知データは、Web画面と将来のWeb Push、ネイティブPush、アプリアイコン未読数が同じsource eventを使える構造にした。初期Web版は一覧・未読badge・既読管理までとし、Push／Email／Realtimeは含めない。本番DB適用と人間QAは未完了である。

## 人間による画面確認が必要な事項

- 現在のヘッダー、下部ナビゲーション、Garage内メニューがスマートフォンで競合していないか。
- 「ホーム」と「フィード」を分けることが、αテスターの再訪理由を強めるか。
- 中央の「記録する」が強すぎて閲覧・発見を妨げないか。
