## 1. Executive Verdict

**90日の検証は続ける。ただし、Barchetta専用の情報サービスを先に作る戦略から、「次の整備相談に使える本人の履歴」と「参照した情報に対する後日の結果」を、接点のある趣味車Ownerで確かめる戦略へ変える。** BarchettaはFounderの実験基準車とする。獲得対象を一車種へ限定する根拠は、今回の接点制約で弱くなった。

最初の価値は「情報を探したあとも、この車の経緯と結果が手元に残り、次に説明し直さずに使えること」。他車の結果付き事例と外部Webは、その価値を補う候補である。本人の履歴が使われることと、他車に役立つKnowledgeが育つことは別々に証明する。記録アプリとして便利でも、Knowledge事業として成立したとは言わない。

Open Web Groundingは**PROTOTYPE ONLYとして条件付き採用、本番機能は未採用**。まず人が参照元を整理する小規模実験にする。Googleとの比較に加え、外部Webだけの整理に内部Evidenceを追加した差分を測る。Webで回答が便利になっても、結果が戻らず固有Evidenceが再利用されなければ、独自の検索AIへの投資を止める。

Professionalは**VALIDATION ONLY**。ベテラン整備士のGoogle AI利用は、現場で観察すべき行動の存在を示すn=1の報告である。課金の根拠にも、専用AIの需要証明にもならない。主な買い手は当面Ownerとして検証し、工場の情報整理・説明・再来店時の引継ぎに独立した支払理由があるかを並行して調べる。

最大の停止条件は、入力の重大な不具合を解消し、利用機会のある外部Ownerを2つの募集群で観察しても、本人の履歴再利用が成立せず、内部Evidenceにも外部Webを上回る実用上の差が出ないこと。その場合、統合Knowledge事業への投資を止める。Web検索を足して延命しない。片側だけ成立した場合は、その価値へ縮小する（§20）。

## 4. Open Web Grounding Verdict

**採用するのは検証手段。採用しないのは、今から作る万能整備AI・大量収集基盤・外部本文の恒久Knowledge化である。** 新規API契約・送信承認なしでも、通常の検索を人が行い、利用可能な資料から参照カードを手元で整理する実験は設計できる。自動処理はその価値が見えた後に審査する。

| 方式 | 判断 | 理由と限界 |
|---|---|---|
| 本人の履歴＋外部原資料へのリンクを人が整理 | VALIDATE MANUALLY、最初の手段 | 導入費を増やさず需要を確かめる。ただし人の専門知識・編集時間を製品性能と偽らない |
| 許諾済み・利用条件確認済みの少数sourceを用いるquery-time検索／整理 | PROTOTYPE ONLY | Cold Startの需要側を補う候補。網羅性の不足、Provider費、出典保持の条件を実測する |
| 許諾済み資料の小さな固定コレクション | 比較用の代替案 | 開放Webより狭いが再現性・権利確認が容易。限定車種でこれが最も有用ならOpen Webに固執しない |
| 個別sourceごとに全文を取り込み、永続vector DB化 | DEFERではなく初期戦略としてREJECT | 権利・更新・重複・削除・コストに先行投資が大きい。明示ライセンスが必要になった具体用途だけ将来再審査 |
| Googleを使うOwnerに、履歴・結果をMECHORIへ残してもらう | 常に比較に残す低コスト案 | 検索を自社提供しなくても中核価値が成立するなら、こちらを選ぶ |

95/5→60/40→20/80というWeb／内部の比率は説明用の仮説にすぎない。何を分母とするか曖昧で、内部の低品質事例を増やす誘因になる。代わりに「内部の追加で判断準備に実用差が出た案件数」「別の実車で再利用された結果付きEvidence数」「自然な結果返却率」を測る。外部が80%のままでも有用な独自部分で採算が合えばよい。内部80%でもFounder一人の転載なら資産ではない。

## 5. Google AI vs MECHORI

**競争相手は、Googleを使い慣れた人の実際のやり方である。** Googleにもリンク、会話、履歴、個別文脈があるので、「Googleには車の文脈がない」という前提は採らない（§3の公式資料）。MECHORIの余地は、許諾された実車の時系列、改善しなかった結果、再発、確認者、共有範囲を、次の相談へ取り出しやすく保てるかにある。この余地も未検証である。

**四群比較の実験契約**

| 群 | 利用できる根拠 | 切り分ける問い |
|---|---|---|
| A: Google Search / Google AI | 普段使うGoogleと公開Web。AI表示の有無・利用機能・地域・日付を記録 | 現行代替手段より乗り換える理由があるか |
| B: internal only | 利用権限のある実際のMECHORI／本人提供Evidenceのみ。DEMO・創作は禁止 | 内部だけでどの問いに答えられ、どこが空か |
| C: external only | 外部WebをMECHORI式の参照カードへ整理 | 表示・条件整理・手動編集の価値があるか |
| D: external + internal | Cと同じ外部資料集合に、許諾された内部Evidenceを追加 | 同じ見せ方・作成資源でも内部Evidenceが差を生むか |

最初にFounderの実在資料で最大6題を作り、評価方法を調整する。列挙された部品・症状は実例の保証ではない。検証できる資料が3題しかなければ3題で行い、足りない実例を作らない。この調整群を合格率に入れない。

本人提供資料をB/Dで利用する場合、既にMECHORIへ記録された実例と、実験のために新たに提供された資料を区別する。後者の有用性は「そのような資料を将来集められれば得られる差」であり、現在のMECHORIにその資産が蓄積済みという証明ではない。供給に必要だった依頼・整理時間も記録する。

次に**Founder以外の6人以上、合計12題**を未使用の評価群にする。2車種以上を含め、利用機会・外部資料の有無・関連内部Evidenceの有無を回答作成前に分類する。1人の題数は最大2。内部あり題を目安6、内部なし／薄い題を目安6とするが、実在しない内部Evidenceを埋めない。確保できなければ内部優位の結論は保留し、密度獲得の失敗として別に判断する。

共通の車両仕様、利用者がその時点で知っていた履歴・質問文は全群に同じだけ渡す。Aにも本人が通常使える背景説明を許す。Dの追加根拠は、この共通説明とは別の、検索対象となる過去実例である。**その題の後日判明した結果・修理の正解は全群から隠す**。同一案件の再投稿、翻訳、要約を検索に残さず、少なくとも案件単位で隔離する。本人の過去履歴検索と、他車のEvidence追加を分けて採点する。Dがよい理由が単なる長い入力かを疑い、重要な差が出た題ではAへ同じ追加資料を本人が提示する補助比較も行う。

CとDの編集者・手順・許可されたAIモデル・入力上限・外部資料は共通にする。AI利用の承認がない初期は両方とも人が作成し、**人による編集の実験結果であってAIの性能評価ではない**と記録する。Bも同じカード形式にする。自動化を導入した際は、手動時の合格を持ち越さず再試験する。Aは普段のGoogle操作の結果を残し、都合のよいAI回答だけを後から選ばない。AIが表示されなければ通常検索の結果として報告する。

Cの外部資料集合・参照カードは、その題の追加内部Evidenceを編集者が読む前に固定する。編集者が既に内容を知っている場合は汚染の可能性を記録し、未使用評価群では別の資料選定者または盲検化した入力を使う。内部の知識でCの検索queryを密かに改善しない。

作成上限は各群1題15分、利用者の確認時間は別計測する。調整6題＋評価12題の4群で作成時間は最大18時間。採点・訂正・再確認を含め全体32時間までとし、手作業・工場の確認工数も控除せず記録する。C/Dの標準は外部query最大3、読む外部source最大5。B/Dの内部Evidenceは事前に定めた関連条件で最大3件とし、時間上限は同じにする。追加が必要なら「上限内では不足」。将来の採算用には許可された呼出単位・token・再試行を別集計する。

評価者には可能な範囲でブランド名・群名を伏せ、提示順を入れ替える。参照の種類は隠さない。Ownerは自分の用途、整備士2人を目標に専門的な適用範囲と危険表現を評価する。Founderだけで作問・正解決定・採点を兼ねない。整備士が確保できなければProfessionalの信頼と安全性の検証は未了とする。同じ問いを順に見た学習効果は残るため、主評価は各カード単独で記録してから比較する。

評価は各軸0〜2点（不可／限定的／十分）と具体的な理由で残す。ただし合計点が高くても、根拠外の安全関連主張があれば不合格。

| 軸 | 観測すること |
|---|---|
| usefulness・specificity | 本来の相談準備・履歴確認で、どの情報が役立ったかを本人が指せる |
| source transparency | 主張から原資料の該当箇所へ戻れる。リンクがあるだけでは合格しない |
| applicability | 世代・仕様・条件の一致／相違／不明が正しく、異仕様を適用可能と言わない |
| confidence calibration | 不足・相反・未解決を適切に残す。根拠の薄い題ほど断定を控えられる |
| owner / mechanic trust | 信じたい印象ではなく、使った箇所・棄却した箇所・別確認の必要性 |
| time saved | 通常手段との差。読む時間＋作る人の時間を別々に計測し、裏方を隠さない |
| actionability | 「次の相談で確認したい事項」「履歴の取り出し」が具体化したか。修理の実行率ではない |
| result feedback potential | 結果を残したい意向と、実際の後日追記を区別する |

「実用上の勝ち」は、重大な適用誤りがなく、相手群では得られない有用な根拠を確認できた、または同等以上の根拠確認を20%以上少ない利用時間でできた題とする。見栄え・好みだけでは勝ちにしない。20%は測定誤差に埋もれない差を狙う仮の実務基準である。

C対Aは12題中8題以上の勝ちを継続目安とする。D対Cは**内部ありの6題中4題以上**、かつFounder以外の3人以上で追加価値が説明できることを目安とする。全12題と内部あり／なしの内訳を併記し、内部なしでDが有利になるかのように集計しない。差がないときも安全・信頼の悪化を隠さない。小標本なので市場一般の優位性や統計的確証を主張しない。

この比較とは別に、自然に発生した12件以上の情報利用案件（6人以上）を30日追う。記録には参照カード、相談に使った点、後日の観察・未解決・結果を本人確認のうえでつなぐ。観測窓は参照利用から30日とし、その途中で予定された確認機会が到来したかを別記録する。早期に追記されても同じ30日窓で集計し、作業がなかった場合も理由を残す。追記を求める連絡は同意した1回まで。「よかったら直してみて」という実験にはしない。時間内に発生しない結果を成功にも失敗にも捏造せず、§19の分母で報告する。

## 6. Revised Core Value Proposition

Ownerへの価値仮説は、**「この車で何が起き、何を確かめ、その後どうなったかを残し、次の相談で使える」**。検索は入口になり得るが、回答消費で終わらない履歴が中心である。

| 候補 | 位置づけ | 成立条件 |
|---|---|---|
| A 自分のVehicle History | PRIMARY VALUE | 記録した満足ではなく、別日に具体的な用途で取り出せる |
| B 他OwnerのEvidence再利用 | SUPPORTING VALUE、Knowledge事業の必須検証 | 独立した他車の実例が、条件を確認したうえで役立つ |
| C 世界のWebを車両文脈で整理 | SUPPORTING VALUE、PROTOTYPE ONLY | Google等をそのまま使うより有用で、原価・権利が成立 |
| D OwnerとMechanicの結果循環 | SUPPORTING VALUE、将来の差別化候補 | 工場確認を必須入力にせず、本人の記録から始めても回る |
| E 趣味車Community | FUTURE VALUE | 実例の再利用と投稿が自然に増えた後。交流の頻度だけで成功としない |
| F 次の相談へ渡す最小の経緯と結果 | Aを具体化するPRIMARYの利用場面 | 時間のないOwnerが、記憶・写真・紙を探す負担を減らせる |

履歴だけなら、既存のメモ・写真・無料整備記録サービスが強い代替になる（v1 §6参照）。それでも選ばれる理由を手動で見つける。BとDが育たなければ、Aを小さく有料運営する可能性は残るが、Evidenceネットワークとしての成長仮説は取り下げる。

## 7. Revised Beachhead Strategy

**推奨はE:「日本語で参加でき、Founderから連絡できる経路があり、今後30日以内に履歴参照・整備相談・経過確認の機会がある趣味車Owner」**。運用はBの2-trackを使い、Cの広い車種分類を最初から一つのEvidence市場として扱わない。最初の10人を得た後、到達可能な1〜2の仕様群だけで同型車再利用を試す。

以下はアクセス情報に基づく定性比較であり、未計測の人数・頻度・転換率を点数化した市場ランキングではない。

| 案 | 接点・獲得難易度 | 密度・Contribution頻度 | Founder偏り・再利用 | Cold Start・他市場への移転 | 費用・速度・収益への含意 |
|---|---|---|---|---|---|
| A Barchettaのみ | Founder本人以外の確実な人数不明。専用募集が必要 | 集まれば仕様密度は高い。整備頻度は未測定 | Founderと一車種への偏り大。同型の候補は作りやすい | 外部情報はあり得るが実車結果は別。一般化は弱い | 募集待ちで遅延。ニッチ規模・支払人数が制約になる |

| | Track A: Founder Barchetta | Track B: 外部Ownerの複数趣味車 |
|---|---|---|
| 用途 | 出典のつながり、経緯・結果の表し方、Web比較手順を調整 | 記録、再訪、同じ案件の追記、履歴提示、他車への適用、共有需要を評価 |
| 最初の材料 | 実在し利用権を確認した最大6題。深い履歴があるとの仮定は置かない | 既存α＋新規参加者。本人が選ぶ1件から始める |
| 数えないもの | 自分の使いやすさをActivation率、課金率、独立車両密度に混ぜない | 写真好き・交流好きだけの利用をEvidence再利用へ混ぜない |
| 役割の限界 | 一実車の多くの追記は、独立した多数実例にはならない | 多車種でCaptureができても同型Knowledgeの価値は証明されない |
| 次の判断 | 比較に適した題材がなければ参照車を追加／変更 | 到達可能な仕様群を選び、他者Evidenceの再利用を別実験にする |

**Vehicle clusterは「旧車全般」ではない。** 車系統・世代・engine・市場仕様・条件が比較可能な範囲を、[VEHICLE_IDENTITY](VEHICLE_IDENTITY.md)に沿って明示する。別車種の同一engineや部品も、資料上の共通性と相違を確認できた場合にだけ限定的に束ねる。部品番号を推測しない。

Day 28までに、参加者の実際の情報ニーズ上位3テーマを整理する。そのうち少なくとも1テーマについて、Founder以外の3実車から独立した利用可能な記録を集められる仕様群を1つ選ぶ。これは安全な結論を出せる最低件数ではなく、再利用実験を始められる小さな密度の目安。集まらなければ、Barchetta固定へ戻らず、本人履歴検証を継続しながらcluster獲得仮説を止める／一度だけ別群へ変更する。

## 9. Cold Start Strategy

Cold Startには、①初回に得る価値、②他者に再利用可能な供給、③供給者へ戻る便益、の3つがある。外部Webが解くのは主に①であり、②と③は自動的に解けない。

| 手段 | 最初に埋める不足 | 採用順・条件 | 主な失敗要因 |
|---|---|---|---|
| 1 Founder seeded records | 見せ方・実験材料 | 最初に実在分だけ整理、工数上限あり | Founder一人の詳しさを市場の供給能力と誤認 |
| 2 車種／仕様の密度 | 他車への適用可能な結果 | Day 28以降、接点が証明できた1群 | 存在する車種人口と到達可能人口の混同 |
| 3 既存αのContribution | 本人の履歴と入力の現実 | Week 1から任意の1案件を追う | 好意・督促・代理入力による見せかけの継続 |
| 4 ProfessionalのContribution | 内容確認・作業と結果のつながり | 既存工場への観察相談から、手動で少数 | 忙しさ、非公開ノウハウ、顧客同意、無償協力の限界 |
| 5 Open Web Grounding | 内部にない参照材料 | 四群比較だけに限定 | Googleとの差がない／結果が戻らない |
| 6 Public Share / SEO | 新規流入 | まずOwnerが選んだ内容の提示・紹介需要。匿名公開は準備完了後 | 権利・QA未了のまま公開。薄いページ量産 |
| 7 Manual curation | 条件・出所・結果の欠落 | 参照カードを少量作成、本人確認を得る | 記録を創作・美化する／裏方工数で赤字 |
| 8 部品／症状ページ | 具体的な検索入口 | 自分たちに利用可能な独立Evidenceがある題だけ、後段で最大3ページ | 車種別の空ページ、誤適合、更新できない情報 |
| 9 既存の紙・写真・メモを相談用にまとめ、本人へ返す | 初日からの本人価値 | 最優先。各人1案件、初回支援30分以内 | 一度きりの資料整理代行に留まり、本人が戻らない |

推奨順は9＋3→1＋7→5の小実験→2＋4→6→8。支援で作った記録は支援ありと明示する。検索で外部を使ったときも、結果記録の見返し先を本人の履歴にする。投稿の報酬はまず「次に同じ説明をやり直さずに済むこと」。公開への同意、工場確認、課金を初回保存の条件にしない。

同意された連絡で後日の状態を一度尋ねる。改善だけでなく、変化なし・再発・未解決・まだ確認していない、も有効な結果として残す。Ownerが残したい範囲と他者検索への許諾を分ける。私的履歴が増えた量を、そのまま共有Knowledgeの供給量へ算入しない。

## 10. Evidence / Trust Architecture Changes

**A〜Fの一本道の信頼ランクはREJECT。** 公式文書でも市場仕様が違えば当該車両へ適用できない。Ownerの一実車の経過はその車の事実として役立ち得るが、一般的因果関係の証明にはならない。Professionalの署名も、確認した範囲と時点を超える保証ではない。

代わりに、既存[TRUST_AND_VERIFICATION](TRUST_AND_VERIFICATION.md)を拡張する次の直交した属性を提案する。今回はschema変更をしない。

| 軸 | 記録する区別 |
|---|---|
| 出自 | 公式／外部Professional／外部Owner・forum／MECHORI Owner／MECHORI Professional。AI整理は生成方法の属性として重ね、証人にしない |
| 主張の種別 | 観察、報告された作業、使用部品、結果、推測、参照資料の記述。主張を一つの真偽ラベルへ潰さない |
| 確認 | 本人申告、本人資料、確認者・対象・日時、独立追認。所属確認と内容確認を分離 |
| 適用範囲 | 車系統、世代、engine、市場、仕様、発生条件について一致・相違・不明 |
| 時間 | 発生日、資料公開／改訂日、取得日、結果確認日、観測期間。再発なしの観測期間を省略しない |
| 独立性 | 原報告ID、同じ実車イベント、引用／転載／翻訳の関係。不明を独立扱いしない |
| 権利と閲覧 | 権利者、許諾範囲と版、閲覧対象、外部AI送信可否、保存期限、撤回・訂正 |
| 不確実性・相反 | 未解決、別結果、根拠消失、仕様不明、確認待ち。一般化の制約を保持 |

**Reference → Supported Claim → MECHORI Evidenceは、自動昇格の階段ではない。** 外部Referenceに、引用可能な該当箇所、sourceの確認、仕様・時点、主張との対応、利用根拠が揃えば、そのReferenceに支持された主張として扱える。しかし出自は外部のまま。工場が記事を読んで同意しても、独立した実車結果は増えない。

新しいMECHORI Evidenceになるのは、別途実在するOwner／工場の観察・作業・結果を、本人が確認して記録したイベントである。参照した外部記事との関係は残すが、元記事の文章・画像・権利を取り込んだことにはならない。自社Evidenceという言葉もMECHORIによる著作権所有を意味しない。寄稿者の権利、私的利用、共有利用、引継ぎ許諾は別に保持する。外部記事の著者本人から改めて寄稿・許諾を得た場合も、原掲載先との由来を残し、同じ事例を二重計上しない。

**保存と撤回の最小契約案**

基本候補は参照ID、canonical URL、必要なtitle／metadata、取得・確認時点、主張との関係、独立性の注記、利用根拠と期限である。URLやtitleを含むAPI結果にも契約上の制限があり得るため、「metadataなら無条件保存可」としない。短い引用・AI要約は必要かつ利用可能なものだけ。全文・画像・embeddingの永続保存は初期対象外。ライセンス不明の場合は本文処理を除外し、リンク保存自体の条件も確認する。

取得時に期限を記録し、期限切れ・権利撤回・訂正を参照カードと派生要約へ伝播させる。cache利用可否と期間はProvider・権利者条件に従う。公開要約に私有履歴を混ぜず、非公開の個別要約を共有する際は改めて閲覧権限を評価する。ユーザーの記録撤回後も古い要約から内容が読める設計を避ける。観測の原本を一般ログへ複製しない。

**既存方針との差分は明示して採用審査へ回す。** [AI_POLICY](AI_POLICY.md)と[KNOWLEDGE_SYNTHESIS](KNOWLEDGE_SYNTHESIS.md)は現時点で公開KnowledgeCaseに基づく整理を中心とし、AIに未知の情報を検索させない。v2の本番Groundingはこの範囲を広げる候補であり、既存許可の延長ではない。新しい入力範囲、source許諾、個人情報除去、Provider保持条件、上限、出力検証、縮退を具体化した別審査が必要になる。

[AI_CRAWLING_POLICY](AI_CRAWLING_POLICY.md)で自社への無許諾の外部Knowledge化を拒みながら、他サイトには無許諾で同じ行為をするという非対称な前提を置かない。通常検索で発見することと再利用の権利を区別する。採用時の文書更新先はAI_POLICY、KNOWLEDGE_SYNTHESIS、TRUST_AND_VERIFICATION、IMPORT_PIPELINE、PRIVACY、AI_CRAWLING_POLICY、INFRASTRUCTURE_COST。現行規則を本書で黙って上書きしない。

## 13. Owner Strategy

Ownerの入口は「全部の記録を移してください」ではなく、「次の相談で使いたい1件を選ぶ」。本人の写真・紙・メモのうち必要な部分だけを、本人が確認して履歴へ残す。初回30分以内の支援を上限とし、原本・顧客名・車台番号を新たな外部AIへ送らない。

現αの保存経路・共有範囲を先に説明し、設計上のprivate defaultを実装済みと案内しない。現行の共有条件に合わない資料は投入せず、本人の手元で確認する手動実験に留める。私的履歴を他者向け検索へ使うことは、今回の戦略提案から自動的に許可されない。

次に、別日にその記録を自力で探し、相談・履歴確認・過去との比較のどれかへ使えるかを見る。戻る理由は通知の多さで作らず、本人が予定している確認時点に合わせる。結果追記は短くできる見せ方を手動で試すが、現在未実装のExperience relationを完成済みと説明しない。

Ownerの便益は、情報検索の速さ、説明し直す時間、記憶の抜け、再発時の参照を減らすこと。趣味の写真・思い出の価値は否定しないが、Evidence事業のKPIとは分ける。継続頻度の低いOwnerへ毎月のAI利用を強要せず、年払いの履歴機能と必要時の有償整理を別候補として比較する。

最初の30日で次の自然な利用機会がない人には、無意味な投稿を促さない。参加者全員の再訪率と利用機会がある人の再利用率を両方見る。結果を残すこと、失敗・未解決を報告すること、自分の記録を読んだり持ち出したりすることを課金の条件にしない。公開Contributionは常に任意とする。

**Groundingの原価と月5,000円制約**

Braveの公開Search料金は1,000 requestsあたりUS$5、月US$5 creditの案内がある。Search APIの保存権・第三者本文の利用権は別途確認が必要であり、今回契約を選定・追加していない。[公式料金・FAQ](https://brave.com/search/api/)

以下はProvider比較の結論ではなく、呼出が増えると何が起きるかの感度分析。為替160円/US$は現相場ではなく計画用仮定。credit・cache割引は予算に織り込まない。税込相当の安全側見積もり、為替手数料、課金単位、実AI単価、検索結果の権利追加費は接続前に確認する。

`1案件の費用 c = 検索呼出数 s × 0.8円 × 再試行等の倍率 r ＋ AI整理費 a ＋ その他の増分費`

仮にs=3、r=1.2、その他増分0とすると、検索費2.88円。AI整理費a=2円ならc=4.88円、a=8円ならc=10.88円。AIの2円／8円は特定モデルの価格主張ではなく、入力増加を含む試算レンジ。モデル選択・導入はしていない。本文取得・storage・監視等の追加費があればcまたは基盤費へ必ず加える。

| 月の処理案件数Q | c=4.88円の場合 | c=10.88円の場合 | その他基盤2,500円＋予備500円を加えた総額（低／高） |
|---|---:|---:|---:|
| 100 | 488円 | 1,088円 | 3,488／4,088円 |
| 180 | 878.40円 | 1,958.40円 | 3,878.40／4,958.40円 |
| 500 | 2,440円 | 5,440円 | 5,440／8,440円 |
| 2,000 | 9,760円 | 21,760円 | 12,760／24,760円 |

基盤2,500円と予備500円は予算配分の例で、現在の実請求ではない。実際のhosting、DB、storage、認証、メール、監視、解析、その他継続費の合計をまず確認する。その他基盤が2,500円以下という条件で、Groundingに最大2,000円を確保するなら、高い方の想定でも月180案件程度が上限となる。これは接続の許可でも、誰にでも与える無料quotaでもない。

承認後の実装案では、月次残額と各処理の最大費用を呼出前に確認し、input・output・query・retryを制限、予約原価を差し引いてから並列処理を許可する。料金や権利費が試算上限を超えれば呼び出さない。利用者別上限と全体上限を両方置く。cacheは許諾された範囲だけで使う。上限で外部リンクや自分の履歴に戻り、繰り返し課金する自動fallbackを禁止する。残余予算は `5,000円−確認済み全継続費−予備` から再計算する。

より安価な代替は、既存Google検索＋MECHORIの本人履歴、リンクのみの整理、少数の許諾資料、人による限定検証。導入を延期するとアプリ内での即時回答は検証できないが、独自履歴の価値・参照の見せ方・結果返却は検証できる。無料creditがあっても、新規従量課金・契約・本番AI送信は所有者の個別承認まで開始しない。

**支援費を含む単位採算（仮定）**

Founder時間はv1と同じ仮の時給3,000円、決済費5%、利用者ごとのその他増分20円/月とする。月のContribution marginは、売上からこの決済・増分・検索AI・直接支援を引いた額。固定費・獲得・開発・一般運営・税を引く前であり、手取り収入ではない。

## 17. Moat / Network Effect

現時点でMoatやNetwork Effectは確認できない。AI chat、RAG、Search API、UI、モデル選択、外部Web検索は再現可能な実装である。

| 資産候補 | 蓄積に必要なこと | 防御力の限界／証拠にする指標 |
|---|---|---|
| 実車の長期履歴 | 同一実車の別日の観察・結果・再発、訂正を保つ | Ownerは他サービスへ持ち出せるべき。件数より、別日に取り出して役立った履歴数 |
| 結果と再発 | 観測期間、変化なし、未解決、独立した別車両を含む | 自己申告や短期改善だけでは弱い。追記率と別車再利用の増加 |
| 車両条件とprovenance | 条件一致・不明、原資料、確認範囲を維持 | 手作業で高価になり得る。根拠確認時間が減るかと運営負担 |
| Owner／工場の関係 | 双方に再利用の便益、許諾と非公開ノウハウ保護 | 人間関係だけに依存すればFounderの代行業。Founder不在時の継続 |
| 再利用の履歴 | どのEvidenceがどの案件で役立ち、どうなったか | 利用回数は正しさの証明ではない。結果追加が後続の有用性を増やした差 |
| 権利・承継 | 誰が何を共有・引継ぎできるかを追跡 | 設計だけでは資産でない。無断独占やデータ拘束をMoatにしない |
| 高密度の仕様群 | 他者の反復ニーズに対する独立した結果 | 広い全車種DBより小群で検証。別clusterへの移転には再検証が必要 |

Network Effect候補と呼べる因果は、**同条件の独立した結果が増える→次のOwnerが既存Webだけでは得られない条件・経過を使える→そのOwner自身の履歴に結果を残す便益があり、任意共有が増える→次の独立結果が増える**、である。この全段が観測されるまでは「目指す循環」と呼ぶ。

因果を確認するには、同じ外部資料・同程度の質問で新しい内部結果を加える前後、またはD対Cで有用性の増分を見る。その後、支援・督促の有無を分けて結果が追加されたかを追う。単に利用者が増えた時期に投稿も増えたという相関では足りない。データが増えるほど条件違い・spam・管理負担で価値が下がる負の効果も計測する。

Googleや他社が同じ機能を出した場合、残り得るのは利用者が継続して使い、適切な権利で提供した経緯と結果への関係である。ただし大手も本人資料の取込・継続保存を提供できる。OwnerがGoogleへ同じ履歴を渡す補助比較で差が消え、戻る理由もなければ、Moat主張を取り下げる。全データを公開して模倣不能と称することも、閉じ込めて維持することも採らない。

## 19. KPI

| Contributor resurrection | 30日投稿がなかった人が新たな自然の利用機会に本人確認済みの記録を追加／30日休止し、次の30日窓が満了した人 | 再連絡あり／なしを分離。時期的に母数がなければ未測定 |

Completed Evidence Loopは、本人が明示した同一案件について、Intake→別日の具体的再利用→後日の確認済み結果が追跡できる場合にだけ数える。現αの近い日時・似た本文から自動推測しない。1案件を連続クリックで複数loopにしない。共有利用可能なloop、私的loop、別車再利用loopを分ける。

手動台帳の最小項目は仮名の参加者ID・実験案件ID・source参照ID・同意範囲・時点・用途分類・支援分数・結果分類・観測窓・群・実用差の理由。詳細記録は権限のある原本を参照し、Gitや外部解析に複製しない。集計は人数と件数を併記し、率の見栄えを良くするために失敗・撤回・未回答を除かない。

閾値は小規模な経営判断のための仮説であり、有意差や普遍的な基準ではない。nと分母の条件、具体例、支援量を必ず併記する。外部Owner6人の12題を独立した12人の調査と表現しない。

## 20. Continue / Pivot / Kill Criteria

CONTINUEは次の小さな検証への進行であり、PMF認定ではない。PIVOTは価値・対象・提供方法を一度絞り直すこと。KILLはその仮説への新規投資を止めること。利用者データの削除やサービスの突然の停止を意味しない。

数値は開始前に固定し、結果が悪いから変更しない。母数不足では「不成立」と「未検証」を区別するが、未検証のまま大型機能を解禁しない。90日内の修正再試験は主要仮説につき1回、同じ支援上限で行う。十分な母数に届かない獲得経路は、時間上限で止める。

| 仮説 | CONTINUE | PIVOT | KILL／投資停止 |
|---|---|---|---|
| 1 Self-history value | 利用機会あり・30日満了の10人中7人以上が自力で別日再利用し、具体用途が説明できる | 3〜6/10、または手厚い支援時だけ成立。用途・入力を1回修正し、新しい10人で再確認 | 重大なUX阻害を解消後も、2つの10人cohortで各2人以下。統合Owner履歴への追加開発を止める |
| 2 他者Evidence reuse | Founder外10人以上・20試行で12件以上が有用、少なくとも5人に便益。仕様群別にも確認 | 6〜11/20、または1人・1sourceに集中。対象仕様・用途を一度狭める | 実際の関連Evidenceを揃えた再試験でも5/20以下。全車種Knowledge構想を止め、本人履歴など成立した価値へ |
| 3 Open Web Grounding | §5のCがAに8/12以上実用上の勝ち、重大な品質失敗なし。作成工数・原価も成立する見通し | 勝ち4〜7/12、利用時間は減るが手動依存／権利が狭い。リンク整理・許諾資料限定へ。Cが弱くてもDだけ強ければ内部中心に限定 | 1回修正後もC対A・D対Aがそれぞれ3/12以下の勝ち、または権利・原価を解けない。自社Grounding製品を止める |
| 4 Proprietary Evidence advantage | 内部あり6題中DがCに4題以上勝ち、3人以上に便益。結果返却も6/12以上、うち自発3件以上 | 内部差が2〜3/6、差はあるが返却が少ない、または逆。用途／時点／便益を1回修正 | 内部ありの再試験6題でも差が1題以下、または返却が修正後も2/12以下。Web→固有Evidence循環への投資停止 |
| 5 Public Share acquisition | 権利と計測が整い、200適格訪問から6人以上が初回有用記録、その後の自力利用もある | 2〜5/200、または個別提示でのみ機能。素材・相手を1回変更して再試験 | 再試験の200訪問でも1人以下、または許諾・撤回を実現できない。公開獲得開発を止める。未公開ならNOT RUNでSEO拡張は解禁しない |
| 6 Professional WTP | 実用途を2件以上使った3工場中2工場が具体価格で申込。承認後の実支払・次期更新へ進む | 1/3、特定の帳票用途のみ、または無償協力だけ。対象業務を1回限定 | 2件以上試した工場に修正版を提示しても具体申込0/3、または有償条件では直接採算が負。Professional主収益仮説を止める |
| 7 Owner WTP | 2回以上便益を得た20人中5人以上が具体価格で申込。承認後の実支払・継続へ進む | 2〜4/20、年額は弱いが単発ニーズあり。狭い便利さ・単発へ一度変更 | 修正版でも1/20以下、または無料利用負担込みで採算を改善できない。Owner継続課金の開発を止める |
| 8 Vehicle cluster | Day 28に1テーマ・独立3実車へ到達し、Month 2に仕様を揃えた他者再利用が観測できる | 接点はあるがテーマが散る、別仕様では役立つ。一度別群へ絞る | 別群を試してもDay 60までに必要な密度へ到達できず、募集工数も上限超過。車種集中の獲得投資を止める |

原価と安全は全仮説に優先する。重大な根拠外主張・情報漏えいが見つかれば該当提供を止め、予算上限を超える構成は有効化しない。訂正・未解決の多さ自体を危険や失敗としない。

**事業全体のDay 90判断**

- 本人履歴＋他者／内部追加価値＋いずれかの料金付き需要が成立し、原価・時間の見通しがある: 次の小規模な有料検証へ。申込だけならPMFや売上を宣言しない。
- 本人履歴だけ成立: 小さなOwner履歴サービスへ縮小し、Knowledge／AIネットワークの投資を止める。独立採算と低頻度の継続を追加確認する。
- 他者Evidence／工場業務だけ成立: 対象群と業務を絞った手動サービスを検証。汎用Ownerアプリの拡大を止める。
- Webの読みやすさだけ成立し、記録・結果・固有差がない: MECHORI独自の検索AIは止める。Google等の既存手段に任せる。
- 本人履歴も内部追加価値も失敗、または募集・運営が上限内で成立しない: 統合Knowledge事業への追加投資を停止し、維持・データ出力を含む縮小方針を所有者が判断する。

支払試験に必要な適格者や承認が揃わなかった場合は、失敗と捏造しない。ただし「需要はあるはず」として次の大規模開発へ進めない。延長するなら、既に強い便益の証拠があり、残る一つの問い・対象者・期限・時間上限を明示できる場合だけ、所有者が判断する。

## 21. Founder Time Allocation

週20時間の配分例。実稼働が少ない場合は同比率で減らす。無料協力、課題整理、原資料確認も実時間として記録し、夜間Codexの出力を人間による確認不要な完成物として数えない。

| 活動 | 比率 | 週の時間 | 使途 |
|---|---:|---:|---|
| Product | 10% | 2時間 | 仮説、比較カード、何を捨てるか、次の判断 |
| Engineering | 20% | 4時間 | 再現P1、保存・再表示、検証済み用途の最小改善 |
| User Interview | 20% | 4時間 | Ownerの実利用観察、比較採点、別日再利用 |
| Tester Support | 10% | 2時間 | 初回30分以内の支援、失敗の記録、同意したfollow-up |
| Community | 10% | 2時間 | 接点のあるOwner／管理者との関係と許可の確認 |
| Research | 10% | 2時間 | 比較に必要なsource、権利、適用範囲、原価だけ |
| Marketing | 5% | 1時間 | 本人が許可した実例と募集説明、転換観測 |
| Business Development | 10% | 2時間 | 工場の業務・紹介・価格付き提案 |
| Operations | 5% | 1時間 | 費用、権限、集計、checkpoint、判断記録 |
| 合計 | 100% | 20時間 | 約257時間／90日 |

Webの比較作成はResearchとProduct、Owner採点はInterview、工場評価はBusiness Developmentへ計上し、同じ時間を二重計上しない。Researchだけで全比較を背負えないので、§18の32時間枠をこれらから割り当てる。Week 1–4の獲得関連12時間上限もCommunity／Marketing／Business Developmentの内数とする。

2週間連続で支援や運営が枠を超えたら、新規募集と新機能を減らす。人が確認し続けないと安全に使えない回答は、安いAI製品の採算で扱わない。需要を見ずにEngineering比率を増やすことを禁止し、増やす場合は解消する実利用の阻害と削る活動を明示する。

## 23. Three-Year Success Scenario

これは予測ではなく、明確なPMFがあるなら何が積み上がっている必要があるかの逆算。登録者・投稿総量・売上の大きな数字で成功を定義しない。

| 年 | 増えるEvidence Asset | 競争力が増す理由 | その年に必要な証拠 |
|---|---|---|---|
| Year 1 | Founder以外の複数実車に、本人確認済みの経緯・結果・観測期間が連続し、許諾範囲と出典が整理される。1仕様群で他者再利用が発生 | 単発のWeb記事では分からない、その車の前後関係を次回の相談で使える | 本人再利用とD対Cの差、実支払、支援時間、訂正・撤回運用。Founderが全記録を代行しない |
| Year 2 | 同じテーマで別実車の結果、再発、変化なしが追加され、再利用先から新たな観察が返る。Ownerと一部工場が自ら追記する | 条件差・失敗例・経過まで分かる小さな密度が、探索と説明の負担を減らす | 新しいEvidenceを加えた実用差、Founder介入の低下、有料の更新、隣接1群での再現 |
| Year 3 | 複数の限定群で長期履歴と独立した結果が育ち、許可された引継ぎ・修正・再利用の関係が維持される | 新規Ownerにも価値を渡せる一方、継続Ownerが自分の履歴へ結果を返す理由がある | 有料cohortの継続、獲得費回収、無料分を含む原価、運営余力。Googleへ同じ資料を渡す比較でも継続利用の理由が残る |

最も現実的なのは、世界中の整備情報を覆うサービスではなく、まず少数の趣味車Ownerが次の相談に使い、結果を残す習慣ができ、その一部の仕様群で他者にも役立つ事例が育つ筋道である。収益源はOwnerの反復便益か、実測で成立した工場業務のどちらかに絞ってよい。Open Webは探索の補助として残っても、利用者自身がGoogleを使う構成になってもよい。

権利が複雑な公開情報を大量に持つことより、戻ってくる実車の経過、適用範囲、確認者、利用許諾を失わずに増やすことが重要。ただし、それが運営負荷だけを増やし他者価値に変わらなければ、3年の継続自体を成功にしない。

## 25. Final Recommendation

**今投資するのは、実車の履歴が次の用途に使われ、結果が戻るかを確認する90日である。** Barchettaはその手順を磨くAnchorにする。獲得は直近の維持課題と接点から始める。Open Webは初期価値を補えるかの小実験であり、事業の中心やMoatとして採用しない。

Professionalは観察と料金付き検証に留め、Ownerと工場のどちらが具体的便益へ支払うかを確かめる。本人の履歴価値と内部Evidenceの追加価値が両方弱い場合は、AIを足すのではなく投資を止める。

**v1から変わったこと（最大10項目）**

1. Barchetta第一beachheadを取り下げ、Anchorと獲得対象を分離した。
2. 既存αを活かし、直近の利用機会を持つ趣味車Ownerを最初の対象とした。
3. Open Web Groundingを条件付きの比較実験へ追加し、本番採用と分けた。
4. Googleとの比較に加え、D対Cで内部Evidenceの追加価値を測るようにした。
5. 外部参照は外部のまま保ち、新しい実車結果だけを独立した寄稿Evidenceとして扱う境界を明確にした。
6. Public Share・Media・Experienceを一律の大型投資にせず、需要と安全な依存解消で順序を決めた。
7. Professionalのn=1観察を、専用AI需要ではなく実案件のworkflow観察へ変換した。
8. 利用機会・自力／支援・Founder／外部・内部あり／なしをKPIと停止条件に組み込んだ。
9. 検索＋AI＋無料利用＋裏方確認工数を採算に加え、月5,000円内でも無制限検索は約束しないことにした。
10. Engineeringを20%へ抑え、90日・12か月の計画を機能日程から条件付きの学習段階へ変えた。

**明日からやること TOP 5**

1. 既存α3名と新規候補について、次の30日に履歴を使う機会・参加意思・紹介経路を確認する。最初の5人を確保する。
2. P-086、P-081/B等の実機QAを行い、ログイン→1件保存→再表示→履歴を探す、のどこが実際に止まるか記録する。
3. FounderのBarchetta資料から実在する最大6題を選び、共通の質問時点・隠す後日結果・利用権限を決める。
4. §5と§19の評価項目・分母・支援時間を最小台帳へ移し、1人の相談用履歴を手動で作って別日利用を予定する。
5. 既知の工場へ最近のGoogle AI利用を見せてもらう相談をし、同時に現在の全継続費と週の実稼働時間を確認する。新規契約はしない。

**今後30日で絶対に作らないもの TOP 5**

1. Nativeアプリとoffline同期基盤。
2. Drive・位置共有・旅行Community機能。
3. 独自Voice録音・文字起こし基盤。
