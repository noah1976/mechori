# IMPORT_PIPELINE

## 文書の目的

紙の整備記録簿、整備明細、PDF、画像等を、ユーザーが確認した非公開の整備履歴へ変換する流れを定義します。現時点では実物資料がないため、帳票固有の読取ルール、OCR精度、対応フォーマットを確定しません。

## 成功条件

- ユーザーが1件ずつゼロから入力する量を減らす。
- 怪しい項目だけを、元資料の該当箇所を見ながら修正できる。
- 1つの資料から複数の整備イベントを作成できる。
- 1回の入庫に複数作業と複数部品を関連付けられる。
- AIやOCRの推測を、確認済み事実として自動保存しない。
- 原本と個人情報を標準で恒久保存しない。

## 工程

### 1. 原本取得

入力候補:

- 複数ページPDF
- 撮影画像
- スキャン画像
- 将来のCSV、音声、本人の過去投稿

取得前に、処理場所、外部送信の有無、原本保存の有無、削除時期を表示します。

### 2. 前処理

- ページ分割
- 回転・傾き補正
- 必要最小限のトリミング
- 画質確認
- 重複ページ候補の検出

原本を書き換えず、処理用派生データとして扱います。

### 3. 文字抽出

初期優先順位:

1. Mac等のローカルOCR
2. 将来のiOS・Android端末内OCR
3. 明示承認したクラウドOCR

出力はページ、領域、行、文字列、Provider確度を関連付けます。手書き、判子、チェック欄、表形式を別々に評価できる形を想定します。

### 4. 個人情報候補の除去

外部AIへ送る前に、氏名、住所、電話番号、ナンバープレート、VIN全文、担当者個人名等の候補を除去またはマスクします。

自動検出を完全とはみなさず、外部送信がある場合は対象範囲をユーザーが確認できるようにします。初期ローカル検証では、匿名化済みテキストだけを次工程へ渡します。

車両写真または書類画像では、次の画像処理もこの工程に含めます。

- ナンバープレート領域の検出候補
- プレート文字・数字を復元できないマスク
- 顔、住所、電話番号、背景に写った他車両のナンバー候補
- EXIF・GPS等の不要なメタデータ除去
- マスク済み派生画像のユーザー確認

公開・共有用画像は、マスク確認が完了しない限り次工程へ進めません。検出失敗を「個人情報なし」と扱わず、ユーザーが手動で範囲を追加できるようにします。

### 5. 構造化候補生成

抽出テキストから次の候補を作ります。

- 整備イベントの日付、走行距離、概要
- 症状・観察事項
- 複数の点検・作業
- 各作業に関連する部品、メーカー、部品番号
- 費用、結果、危険領域候補

ルールベース、手動マッピング、AI Providerを差し替え可能にします。AIは候補生成だけを行い、診断や不足情報の創作を行いません。

走行距離は資料に記載されたメーター表示値と単位を抽出し、累積走行距離へ自動変換しません。過去の表示値より小さくても虚偽やOCR誤りと決めつけず、メーター交換、修理、リセット、桁あふれ、単位変更の可能性を確認候補として提示します。

### 6. 分割・関連付け

次をユーザーが修正できます。

- 複数の入庫を別イベントへ分割
- 同じ入庫のページを1イベントへ結合
- イベント内の複数作業を分割・結合
- 部品を正しい作業へ移動
- 走行距離や費用の適用範囲を変更

### 7. 項目確認

確認状態:

- `READ`: OCRで読み取った候補
- `INFERRED`: 文脈から推測した候補
- `UNREADABLE`: 判別不能
- `NEEDS_REVIEW`: 確度または安全上の理由で要確認
- `USER_CONFIRMED`: ユーザー確認済み
- `REJECTED`: ユーザーが不採用にした候補

必ず確認を促す候補:

- 日付
- 走行距離
- 部品番号
- 費用
- 原因候補
- `CAUTION` / `CRITICAL`に関係する分類
- 共有ナレッジへ含める項目

確認できない値は空欄または未確認で保存でき、もっともらしい値で埋めません。

### 8. 非公開保存

ユーザー確認後、MaintenanceEvent、Observation、MaintenanceAction、PartUsageへ変換して非公開領域へ保存します。

共有は別操作とし、取込完了だけで公開候補や公開状態へ移しません。

### 9. 原本削除

- 通常処理完了後に原本・派生画像を削除する。
- 削除期限、削除状態、削除失敗を追跡する。
- 原本をバックアップへ含めない構成を優先する。
- 例外保存は目的、期限、同意、アクセス権限を明示した場合だけ検討する。

## Provider境界

### OCR Provider

入力: ページ画像と処理設定

出力: ページ・領域付き抽出文字、確度、処理参照ID、利用量、エラー

### PII Redaction Provider

入力: ローカル抽出テキストまたは画像領域

出力: マスク済みデータ、検出候補、ユーザー確認状態

画像ではマスク領域、マスク方式、確認者、確認日時を返します。ナンバープレート文字列そのものを識別・保存する必要はありません。

### Structuring Provider

入力: 匿名化済みテキスト、車両の一般仕様、出力スキーマ

出力: ExtractedCandidateとFieldAssertion。診断結果ではない

### Import Repository

入力: ImportSession、候補、確認操作、削除状態

責務: 再開、重複実行防止、期限切れ削除、個人記録への確定

## エラーと再開

- ページ単位と工程単位で失敗を記録する。
- 一部ページが失敗しても、成功ページを確認できる。
- 再処理でユーザー確認済みの修正を上書きしない。
- 同じファイルの二重投入候補を検出しても、自動削除・自動統合しない。
- 外部Provider停止時は、手入力またはローカル処理へ戻れるようにする。

## セキュリティと費用

- 原本や抽出本文を通常ログへ出力しない。
- ナンバープレートの認識文字列をログ、分析、検索用データへ保存しない。
- 一時ファイル参照を公開URLにしない。
- ユーザー・機能・Provider別にページ数、処理量、費用を計測できる。
- 無料枠超過前に処理停止または回数制限を適用できる。
- Provider追加前に`docs/EXTERNAL_SERVICE_CHECKLIST.md`を作成・確認する。

## 実物資料入手後の検証

最初の3〜5ページでは、次を計測します。

- 印刷文字、手書き、チェック欄、表、判子の混在
- 日付、走行距離、金額の読取率
- メーター交換前後、逆行、km/mile混在を誤って不正扱いしないこと
- 部品名・部品番号の誤読傾向
- 1ページ内の複数作業の分割精度
- ユーザーが修正した項目と修正時間
- 個人情報候補の検出漏れ
- 原本削除までの処理時間と失敗

精度の目標値は資料を確認してから決めます。「全自動登録」ではなく「手入力より修正量が少ないか」を最初の評価軸にします。

## 実物資料がない間に行うこと

- ImportSession、ExtractedCandidate、FieldAssertionの型設計
- ローカルのダミーテキストを使った工程遷移テスト
- 確認画面のワイヤーフロー
- Providerインターフェースと削除処理のテストダブル

ダミー資料でOCR精度、手書き対応、個人情報検出性能を評価したとは扱いません。

## NEEDS_OWNER

- 最初に検証する帳票の種類とページ数
- 原本を端末・ローカルに保持できる最大時間
- 整備工場名を抽出・保存・公開するか
- 費用を保存・公開する場合の粒度
- ローカルOCRで読めない場合にクラウド処理を許可する条件
