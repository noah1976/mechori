# PROFESSIONAL_PLATFORM

## 文書の位置づけ

本書は、MECHORI Professionalを単なる高機能検索プランではなく、趣味車を地域で維持するための工場向け業務基盤へ育てる将来構想です。α・初期MVPの実装範囲ではありません。需要、情報権利、安全性、各国制度、運用原価を段階ごとに検証してから導入します。

## 目指す状態

- 専門店が蓄積した知識を無償で奪わない。
- 専門店から遠い地域でも、地元工場が専門家の知見を借りて受託判断や修理を進められる。
- 工場が記録するほど、自社内の再利用、適切な相談の獲得、相談報酬、ナレッジ還元が増える。
- 整備士が共有・確認・訂正した知見を、本人が管理できる技術ポートフォリオとして積み上げられる。
- オーナー、地元工場、専門店の修理結果が、許諾範囲内で次の事例へ還元される。
- 将来は帳票作成、案件進行、顧客への送付等も扱い、記録と日常業務が分断されない。

日本国内の専門家だけを前提にしません。車両ID、市場名、原文言語、翻訳、単位、通貨、地域別制度を分離し、国境を越えた事例参照と専門家相談へ拡張できる基盤にします。販売・法務・帳票は対象国ごとに段階導入します。

Professional加入だけを、資格、技能、正確性、安全性の保証として表示しません。

## 初期validation hypothesis: Evidence workflow

Professionalの最初の価値は、MECHORI全体のKnowledge Searchだけに依存させません。初期はKnowledge密度が低くても、一つの工場だけで次のEvidence workflowが成立するかを未検証仮説として確認します。

```text
Ownerの車両仕様・過去履歴を受領
  -> 入庫・案件記録
  -> 作業写真・確認・使用部品
  -> 作業結果
  -> 顧客向け報告
  -> Owner履歴へ返却
```

最初は3工場程度の数件の実案件を観察し、一つのworkflowで、入力・聞き取り時間、手戻り、顧客説明、履歴引き継ぎのいずれかが改善するかを測ります。製品を先に売り込まず、現行手順、二重入力、公開可能範囲、支払理由を確認します。同じ課題と価値が再現しない限り、大型Professional SaaSへ進みません。

## 長期三層

Professional / B2Bは、次の三層を順に検証する長期仮説です。

1. **Professional SaaS**: 案件記録、履歴共有、作業報告、自社Evidence検索
2. **Professional Network**: 工場間相談、専門家レビュー、適切な送客、将来の取引・成約手数料
3. **Knowledge Infrastructure**: 許諾・出典付きEvidence API、部品適合・症例data、業務system integration

二層目と三層目は現αのimplementation scopeではありません。Owner Freeが作るEvidence supplyとProfessionalの日常業務を同じEvidence Loopへ接続しますが、非公開の顧客情報・工場ノウハウを自動的に共有資産へ変換しません。

## 個別受託会社化を避ける

工場ごとの要望に応じて、会計、請求、在庫、予約、CRM、汎用ERP、個別受託開発へ無制限に広げません。既存サービス連携が適切な領域を置き換えず、車両履歴と整備EvidenceをOwner・工場・専門家の間で循環させる一つのworkflowから検証します。新しい業務機能は、複数工場で同じ反復課題と測定可能な価値が確認された場合だけ共通Product候補にします。

## Founding Garage

Founding Garageは、正式Professionalの廉価版ではありません。将来のProfessionalを実際の整備現場と共同開発するための、βまでの初期提携制度です。少なくとも1軒の工場・ショップがβまでに参加できる状態を目標にします。

Founding Garageそのものをログインアカウントにはしません。個人ユーザーアカウント、工場・ショップという組織、個人と組織のmembershipを分離し、複数個人が一つの工場に所属でき、個人が複数工場に所属できる多対多を前提にします。

### 工場内のrole

| role | 権限の範囲 |
| --- | --- |
| `representative_admin` / 代表管理者 | 工場プロフィール、メンバー招待・解除、権限変更、将来の契約・所有権移管等 |
| `admin` / 管理者 | プロフィール編集、メンバー管理、工場名義投稿管理、問い合わせ対応 |
| `staff` / スタッフ | 工場管理画面、工場名義の整備実績作成、必要な問い合わせ対応。契約・メンバー権限管理は不可 |

工場名義の投稿は組織へ帰属させ、内部では`created_by_user_id`、`updated_by_user_id`等で実際の操作者を追跡します。membershipが解除された後も、工場の整備実績は工場に残します。

### Platform roleとの分離

工場内roleとは別に、MECHORIの運営権限を持つplatform roleを管理します。創業者の個人アカウントには`platform_super_admin`を付与でき、工場組織作成、事業者確認、Founding Garage資格付与、代表管理者設定、membership・role変更、工場停止・再開、entitlement、モデレーションを行えます。

platform super adminとgarage membershipは完全に分離し、運営者が工場へ操作した場合は、誰が、いつ、どの工場へ、何をしたかを監査可能にします。

### 将来特典

Founding Garage資格は個人ではなく工場組織へ付与します。初期開発に協力した工場には、将来のProfessional基本プラン利用料を継続無償提供する方針です。ただし、高原価AI大量処理、大容量Storage、多数スタッフ追加、広告、取引・決済・送客手数料、個別開発、特別サポートまで永久無料とはしません。

Founding Garage資格と工場内role、資格・所属確認、Professional契約を混同しません。具体的な契約条件、原価負担、終了条件は、βでの実証と法務確認後に定めます。

## β最小基盤（P-085）

実在する店舗・支店を表す`ServiceProvider`と、MECHORI上で権限・契約・entitlementを持つ`ProfessionalOrganization`は別entityとする。Organizationは複数Provider拠点へ拡張でき、初期βではprimary Providerを1件連携する。Founding Garage資格はProviderや個人ではなくOrganizationへ付与する。

個人ユーザーとのmembershipは多対多で、最小roleは`OWNER`と`STAFF`とする。Organization作成時はactive participantの初期OWNERを必須とし、Organization rowとmembershipを同一transactionで作成する。OWNERはOrganization情報とmemberを管理し、STAFFは当面read-onlyとする。既存platform adminはOrganization membershipなしで全Organizationを管理でき、その操作を既存audit logへ記録する。以前の代表管理者／管理者の細分化は、契約・所有権移管を実装する段階まで延期する。

ユーザーの整備記録にProviderを紐づけても、記録ownershipはユーザーに残る。Organizationが後日Providerをclaimしても、過去のユーザー記録を編集・公式確認済みに自動昇格しない。Claim、duplicate merge、Professional-created record、provider-confirmed record、Provider Discoveryは後続段階とする。

## 作業仮説: 整備士のGitHub

Professional側の中核コンセプトを、作業仮説として「整備士のGitHub」と表現します。完成した修理記事を一方向に公開する場所ではなく、個々の事例、未解決事項、確認、訂正、結果追記が履歴として残り、知識と貢献者の実績が一緒に育つ基盤を意味します。

この表現はα版テストユーザーからも「整備士にとってのGitHub（ポートフォリオ）」として挙がった定性シグナルです。既存の内部仮説と利用者の理解が一致し得ることは確認できましたが、整備士本人の継続利用、採用・相談・協業での利用、支払意思までは未検証です。Professional validationでは、言葉への共感だけでなく、実案件から許諾可能な技術実績が自然に残り、本人へ価値が返るかを確認します。

GitHubの画面や用語をそのまま模倣せず、思想を次のように置き換えます。

| GitHubの概念 | MECHORIで扱うもの |
| --- | --- |
| Repository | 車種・世代・仕様・部品・症状に関する知識領域 |
| Issue | 未解決の症状、確認待ち、情報不足の事例 |
| Commit | 実施作業、確認結果、改善・再発、根拠の追加履歴 |
| Pull Request | 知識の追加・訂正・適用範囲変更の提案 |
| Review | 経験者・専門家による根拠付き確認 |
| Maintainer | 特定領域で継続的に確認・整理へ貢献する人 |
| Contribution history | 採用された知見、結果追記、訂正、レビューの履歴 |

車種を単純な一つのRepositoryへ固定しません。同一車名でも年式、型式、エンジン、グレード、市場仕様で異なるため、`docs/VEHICLE_IDENTITY.md`の識別構造を維持し、共通知識と仕様差を追跡します。

この表現は、整備士や工場に価値を伝えるProfessional向けの言葉として優先的に検証します。一般オーナー向け画面へ開発者用語を持ち込まず、「愛車の履歴を次の整備へ生かす」という入口と分けます。

### Professionalの北極星

第一線の整備士や専門家が、宣伝契約ではなく実体験から「これから整備士を続けるならMECHORIへ技術履歴を残したほうがよい」と同業者へ勧める状態を目指します。

その理由はネットワークへ参加しない不安ではなく、次の実利が同時に成立していることです。

- 日々の案件記録が自社の再利用可能な知識になる。
- 許諾した貢献が本人の持ち運べる技術経歴になる。
- 自分の専門領域を必要とする相談、採用、教育、仕事へつながる。
- 世界の類似事例を根拠付きで学び、自分の訂正や結果も次へ還元できる。
- 既存コンテンツ、権利、顧客情報を守りながら参加できる。
- データを出力でき、MECHORIへ閉じ込められない。

有名人の推薦数を成功指標にせず、紹介された整備士が実際に記録・再利用・共有を続け、紹介者と参加者の双方が業務上の価値を確認できたかを評価します。

### 熟練者に耐える中核体験

Professionalが評価される順序は、プロフィールやランキングではなく、実案件で「整備を分かって作られている」と感じられる検索・記録体験を先にします。

1. **仕様差分**: 類似事例とのメーカー、車系統、世代、型式、エンジン、駆動系、市場仕様、発生条件の一致・相違・不明を項目別に表示する。
2. **ケースリプレイ**: 顧客申告、初期観察、原因候補、測定・確認、除外した候補、作業、直後結果、追跡結果を時系列でたどれるようにする。
3. **反対結果**: 改善だけでなく、変化なし、悪化、再発、適合しなかった部品、誤った仮説を同じ重要度で保持・集計する。
4. **測定の前後比較**: 故障コード、電圧、温度、圧力、クリアランス、音・振動等を、単位、条件、測定方法、出典とともに作業前後で比較する。
5. **部品・機構の関係**: 同一エンジン、プラットフォーム、ECU・センサー、OEM供給、品番変更、廃番、流用成功・失敗を、完全互換と断定せず関係種別付きで検索する。
6. **項目別レビュー**: 症例全体への人気投票ではなく、観察、原因候補、確認、適用範囲、部品、安全注意、結果へ根拠付きの確認・訂正提案を行う。
7. **工場の記憶**: 過去案件を担当者、車両仕様、症状、部品、確認、結果から再利用し、担当者が退職しても組織内で経緯を追えるようにする。
8. **現場入力**: 写真・動画・音声と短い発話から作業中の候補記録を作り、後で本人が原文と候補を確認して確定する。音声やAI候補を未確認のまま事実へしない。

MECHORIは最終診断を自動決定せず、「何が一致し、何が異なり、何を確認し、何が直らなかったか」を根拠へ戻れる形で提示します。技術ポートフォリオは、この実案件への採用、確認、訂正、結果追跡から副産物として育てます。

## 技術ポートフォリオ

整備士本人が許可した範囲で、次の事実をプロフィールまたは工場ページに表示できるようにします。

- 対応経験のある車種系統、仕様、症状・作業分野
- 結果まで追跡された事例数帯
- 共有ナレッジとして採用された主張
- 他の専門家による確認・レビュー
- 誤りや適用範囲を訂正した履歴
- 工場間相談で回答し、依頼側から結果報告が戻った事例
- 資格、所属、本人確認等のうち、別途確認できた事項

案件本文や顧客情報を公開しなくても、許諾された対応経験シグナルだけで実績を示せるようにします。工場の実績と個人整備士の実績を混同せず、退職・転職・共同作業時の帰属と表示権限を事前に定めます。

表示は「得意」「名医」「必ず直せる」といった断定ではなく、確認可能な行動と範囲を示します。投稿数、閲覧数、いいね数、Professional契約だけでは技術力を評価しません。安全に関わる作業能力や資格の保証は、貢献履歴とは別の確認情報として扱います。

将来の相談候補表示では、技術ポートフォリオを単純な人気ランキングに使わず、対象車両・仕様・症状、地域、受付可否、言語、根拠種別、結果追跡の有無を個別に照合します。

### 持ち運べる技術経歴書

技術ポートフォリオは、所属工場の集客だけでなく、整備士本人が就職、転職、独立、協業時に使える「持ち運べる技術経歴書」へ育てます。WebエンジニアがGitHub上の継続的な成果を職務経歴の補助に使うように、整備士も確認可能な仕事の履歴を本人の同意で提示できる状態を目指します。

表示・出力候補:

- 一般公開するProfessionalプロフィール
- 採用担当者や協業先だけに見せる期限付き共有URL
- 応募書類へ添付できるPDFまたは機械可読な実績出力
- 対応車種・仕様、作業分野、役割、経験期間のサマリー
- 採用された知見、レビュー、訂正、結果追跡への参照
- 所属先が確認した在籍・担当期間と、本人申告の区別

本人が公開できるのは、自分の貢献事実と許諾済みの概要です。顧客情報、車両個体情報、勤務先の原価・仕入先・独自手順、非公開案件本文を、転職用プロフィールへ自動転記しません。勤務中に作成した知識の権利、退職後も表示できる貢献メタデータ、組織確認の取り下げ条件は、Professional実証前に契約と権限モデルで定めます。

MECHORI上の履歴は国家資格、実技試験、職務経歴書、前職照会の代替ではありません。採用側には、本人申告、所属先確認、第三者レビュー、結果追跡等の根拠種別を分けて提示します。

### 世界で発見される専門性

「整備士のGitHub」は、既に知名度を持つ発信者だけの場ではなく、地域の工場や狭い車種領域で蓄積された技術を世界から発見できる場を目指します。特定車種、エンジン、電装、鈑金、部品再生、地域仕様等の領域ごとに、確認可能な貢献をたどれるようにします。

将来の表示候補:

- 車種・世代・仕様ごとの主要な貢献者
- 症状・作業分野ごとの採用知見とレビュー履歴
- 結果追跡、独立確認、訂正対応の実績
- 原文言語と、翻訳後に別言語圏で参照された実績
- 専門家同士の相談、教育、講師、執筆、採用につながる連絡導線
- 本人が選択した代表事例と専門領域

「世界1位」「第一人者」「Top Mechanic」等を、単一スコアや投稿量だけで運営が認定しません。実績が十分に蓄積した場合も、車種・仕様・分野・期間・根拠を限定し、「この領域で多く採用された貢献者」「結果追跡のある事例を継続して共有」等の説明可能な表示を優先します。

公開ランキングは、人気競争、危険な断定、相互評価の談合、英語圏や大市場への偏り、希少車専門家の過小評価を生みやすいため、初期実装に含めません。まず検索や事例ページから貢献者へたどれる発見導線を作り、比較表示を導入する場合は対象領域、集計期間、根拠、異議申立て、非公開選択を明示します。

著名な整備・DIY発信者は、個人ブランド、教育、工場経営、Right to Repair等の外部ベンチマーク候補として調査します。ただし、外部SNSの登録者数や人気をMECHORI内の技術評価へ直接移植しません。

### 著名な専門家・発信者の参加設計

既に視聴者、工場、教材、スポンサー、相談事業等を持つ専門家へ、無償の再入力やコンテンツ移転を求めません。MECHORIへ参加することで既存活動の価値が増えることを、参加条件にします。

参加価値の候補:

- 本人確認済みの公式プロフィールと、なりすまし防止
- 既存動画・記事・書籍・講座への正規リンクと送客
- 車種・仕様・症状単位で、既存コンテンツが検索から再発見される
- 原文を保ったまま、承認済みの翻訳・索引によって別言語圏へ届く
- 有償相談、工場間レビュー、講師、執筆、採用等の依頼受付
- 許諾ナレッジが有料機能で採用された場合の利用台帳と還元
- 長期的に知識を残すアーカイブと、後継者・共同メンテナーの指定
- どの知見がどの車種・地域で参照され、結果報告へつながったかの分析

参加時の保護:

- 外部コンテンツの本文、画像、動画を無断転載・再学習しない。
- URL登録だけで本人の知識提供や内容保証と扱わない。
- プロフィール、索引、構造化主張、翻訳、AI整理を項目ごとに許諾できる。
- 出典、提供者、原文言語、許諾版、利用先、還元対象を追跡する。
- 誤訳、文脈欠落、適用範囲の誤りを本人が訂正・非公開化できる。
- スポンサー、アフィリエイト、部品提供等の利害関係を表示できる。
- 契約終了後の表示、検索利用、学習利用、収益分配を事前に定める。

最初の著名参加者にはセルフサービス登録を求めず、運営が既存活動を調べた上で、本人が確認・編集できるプロフィール候補と少数の構造化事例を用意するコンシェルジュ型オンボーディングを検証します。著名人だけを優遇して知識の正確性を自動認定せず、確認と権利の基準は他のProfessionalと共通にします。

## 知識を扱う三つの範囲

工場が案件または主張単位で利用範囲を選べるようにします。一件の事例を一括して「公開／非公開」にしません。

### 1. 工場内限定

- 自社の症例、写真、部品、仕入先、診断メモ、帳票を自社だけで検索・再利用する。
- 共有検索、他組織向けAI整理、工場ランキングには利用しない。
- 外部AIへ送る場合は、工場が機能と送信範囲を明示的に選んだ処理に限定する。

工場内限定機能は囲い込みの最終形ではなく、まず安心して記録を始めてもらう入口とします。

### 2. 対応経験シグナル

- 車種群、症状分類、作業分野、対応件数帯、対応地域等の許諾済みメタデータだけを工場案内に使う。
- 独自手順、仕入先、顧客情報、原文メモは開示しない。
- 「対応経験の申告」「結果確認あり」等の根拠種別を表示し、「得意」「必ず直せる」と断定しない。

### 3. 許諾ナレッジ

- 原因候補、確認箇所、使用部品、対応、結果等のうち、工場が許諾した構造化項目だけを共有検索に使う。
- 主張から提供組織、事例ID、許諾版、利用先を追跡できるようにする。
- 原資料をモデルへ恒久学習させず、権限判定後の検索・集計を基本とする。
- 取り下げ、許諾範囲変更、契約終了後の扱いを契約とシステムで定める。

「非公開だがAIが学習し、利用者へ内容を伝える」は実質的な知識利用です。非公開原文のモデル学習を標準にせず、許諾された主張だけを追跡可能な形で利用します。

## 案件完了時の共有導線

工場内記録から、顧客情報と独自部分を除いた共有用候補を作ります。

1. 工場が案件を自社用に記録する。
2. 案件完了時に、共有候補を項目単位で確認する。
3. 工場内限定、対応経験のみ、許諾ナレッジを選ぶ。
4. 公開前に車両識別情報、顧客情報、位置情報、仕入先等を確認する。
5. 許諾版を保存し、後の検索利用を主張単位で記録する。

共有を必須にはしません。共有したほうが業務上の利益を得られる設計で参加を増やします。

## 工場間相談

公開知識だけで地元工場の案件が進まない場合、詳細ノウハウを一般公開せず専門店へ相談できる経路を用意します。

1. 地元工場が顧客情報を除いた車両条件、症状、確認済み事項を入力する。
2. MECHORIが許諾済みの対応経験シグナルから相談候補を提示する。
3. 専門店が受諾可否、料金、回答範囲、予定を提示する。
4. 専門職同士で事例レビュー、追加確認、部品情報等をやり取りする。
5. 地元工場が実車確認と作業判断を行う。
6. 結果のうち双方が許諾した概要を新しい事例候補にする。

MECHORIやAIが整備指示を出す仕組みにはしません。相談者と回答者の資格・本人性確認、責任分界、危険領域、記録保持、紛争対応は実証前に設計します。

## インセンティブ

### 日常業務の価値

- 自社症例の検索・再利用
- 写真、整備記録、部品、原価、説明内容の整理
- OCR、翻訳、重複検出等の入力補助
- 顧客説明用の履歴・作業報告出力
- チーム内の引継ぎと権限管理

### 集客と相談

- 車種、症状、地域、受付条件が合う相談の案内
- 地元工場からの有料事例レビュー
- オーナーからの来店・相談導線

知識投入量だけで表示順位を上げません。低品質入力を誘発しないよう、距離、受付可否、対象車種、対応経験の根拠、言語、相談方式等を分けて表示します。スポンサーや報酬の影響は明示します。

### ナレッジ還元

- 検索・AI整理で採用した事例IDと主張IDを利用台帳へ記録する。
- 閲覧数や「いいね」ではなく、根拠としての採用、利用者の参考評価、結果報告、独立確認等を候補指標とする。
- 初期はProfessional料金の割引または知識クレジットを検証する。
- 規模、税務、本人確認、不正対策が成立した後に、月次の金銭分配を検討する。
- 最低支払額、失効、返金、訂正・削除時の扱いを事前に明示する。

## 工場DXの将来範囲

症例・車両・作業と同じ案件から、次の業務文書候補を作れるようにします。

- 受付票、問診票
- 点検・作業報告書
- 見積書
- 発注書、部品手配記録
- 納品書
- 請求書、領収関連資料
- 顧客向け履歴、次回確認事項

将来はPDF等の出力、印刷、メール等での送信、送信履歴、版管理を検討します。自動送信を標準にせず、宛先、添付版、金額、言語を担当者が確認して実行します。

会計ソフト、電子帳簿、決済、在庫、予約、税務申告を最初から内製しません。既存サービスとの連携で十分な領域と、MECHORI固有の車両・症例情報が価値を持つ領域を分けます。

## 国・地域別帳票

帳票名、必須項目、税表示、番号体系、通貨、端数処理、保存期間、電子送付、電子署名等は国・地域で異なります。単一の世界共通PDFへ押し込みません。

- 共通の案件・取引データ
- 国・地域コード
- 適用制度と版
- 言語・通貨・税区分
- 地域別の入力検証
- 地域別テンプレート
- 人間が確認した適用開始日と変更履歴

を分離する地域パック方式を想定します。

AIやCodexは、公的資料の候補収集、比較、テストケース作成、翻訳補助には使えます。ただし、現行制度への適合判断をAIだけで確定しません。対象国の会計・税務・法務専門家と実際の工場による確認を、地域パック公開の条件にします。

## データ境界の候補

- `ProfessionalOrganization`: 工場・組織と地域
- `OrganizationMember`: メンバー、役割、権限
- `PlatformRole`: MECHORI運営者のplatform roleと監査対象
- `FoundingGarageEntitlement`: 工場組織に付与するFounding Garage資格と条件
- `WorkshopCase`: 顧客情報を分離した案件
- `KnowledgeClaim`: 症例から共有を許諾した主張
- `KnowledgeLicense`: 利用範囲、期間、版、取り下げ条件
- `ExpertiseSignal`: 対応分野と根拠種別
- `ConsultationRequest`: 工場間相談
- `KnowledgeUsage`: 回答で採用した主張と用途
- `ContributionLedger`: 割引、クレジット、分配候補
- `ProfessionalContribution`: 個人・組織の採用、確認、訂正、結果追記の履歴
- `ProfessionalPortfolio`: 本人が公開を許可した経験領域と表示設定
- `BusinessDocument`: 帳票種別、地域パック、版、状態
- `DocumentDelivery`: 送付先、実行者、送付時刻、結果

顧客の氏名、住所、電話番号、ナンバー、VIN全文等を症例検索やナレッジ利用へ混ぜません。帳票業務で必要になる個人情報は、症例ナレッジと別の保持・権限・削除・監査境界に置きます。

## 段階導入

1. βまでに少なくとも1軒のFounding Garage候補へ参加条件を提示
2. 3工場程度への実案件インタビューとEvidence workflow観察
3. Owner履歴受領、案件記録、写真・部品・結果、顧客報告、Owner履歴返却の手作業検証
4. 自社症例庫と共有用概要の負担・権利・再利用価値の検証
5. 対応経験シグナルと相談候補の検証
6. 工場間の有償事例レビュー実証
7. 利用追跡可能なナレッジクレジット
8. 日本向けの作業報告・見積下書き等、限定帳票の実証
9. 既存会計・メールサービス連携
10. 現地確認者を確保できた地域から地域パックを追加

帳票DXをProfessional参加の強い理由として検証しますが、巨大な工場基幹システムを先に作ってPOPOPOと同じ先行投資をしないよう、実際の反復業務から一つずつ進めます。

初期の獲得、価格、国際展開、生活基盤となる収入目標は`docs/BUSINESS_MODEL.md`を参照します。

## 検証指標

- 一件の症例入力・再利用で短縮した時間
- 工場内記録から共有候補を承認した割合
- 対応可能な相談だけが届いた割合
- 工場間相談の受諾、回答、結果報告率
- 知識提供者が対価または業務価値を感じた割合
- 技術ポートフォリオを相談獲得・採用・顧客説明に使いたい整備士の割合
- 公開を許可した実績項目と、非公開を希望した項目
- 帳票の再入力項目と削減時間
- 既存業務ソフトとの二重入力量
- 地域パックの誤り・差戻し・制度更新対応時間
